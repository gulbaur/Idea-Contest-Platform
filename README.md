# Конкурс идей

Сервис внутренних конкурсов идей: сотрудники подают идеи, затем анонимно голосуют, после чего сервис по расписанию закрывает раунды, раскрывает авторов, определяет победителя и рассылает письма. Организатор в реальном времени видит число идей, число проголосовавших и текущие результаты.

> **Статус: в разработке — завершён этап 5 (расписание и почта).** Backend готов полностью: вход, конкурсы со списком участников, идеи, анонимное голосование с отзывом, результаты и победитель, статистика организатора, сигналы WebSocket, напоминания за `REMINDER_LEAD` до конца раунда, итоговые письма и почтовая заглушка. Frontend ещё нет (этап 6). План и статус этапов — [docs/PLAN.md](docs/PLAN.md).

## Предварительные требования

- **Docker** с плагином **Compose v2** (команда `docker compose`):
  - Windows и macOS — Docker Desktop;
  - Linux — Docker Engine и пакет `docker-compose-plugin`.
- Свободный порт `8000` (меняется переменной `BACKEND_PORT`).
- Git — чтобы клонировать репозиторий.

Python, Node.js и PostgreSQL на машине устанавливать не нужно: всё работает в контейнерах.

## Переменные окружения

Файл `.env` **необязателен** — у всех переменных есть значения по умолчанию в [compose.yaml](compose.yaml). Чтобы изменить значения, скопируйте [.env.example](.env.example) в `.env` (Windows: `copy .env.example .env`, Linux/macOS: `cp .env.example .env`).

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | `contest` / `contest` / `contest` | Учётные данные локальной БД (не секрет: БД доступна только внутри Docker-сети) |
| `BACKEND_PORT` | `8000` | Порт backend на машине разработчика |
| `SESSION_TTL_HOURS` | `24` | Срок жизни сессии входа, часов |
| `SEED_DEMO_DATA` | `true` | Создавать демо-аккаунты при старте |
| `DEMO_PASSWORD` | `demo-password` | Общий публичный пароль демо-аккаунтов |
| `REMINDER_LEAD` | `24:00:00` | За сколько до окончания раунда отправлять напоминание: `ЧЧ:ММ:СС` или ISO 8601 (`PT2M`) |

> **`REMINDER_LEAD` меньше суток — только для демонстрации.** Задание требует напоминать за сутки; меньшее значение нужно, чтобы увидеть напоминания вживую, не дожидаясь суток. Значение запоминается в расписании конкурса при его создании, поэтому меняйте его до создания демонстрационного конкурса. Запуск с напоминанием за минуту:
>
> - Windows (PowerShell): `$env:REMINDER_LEAD="00:01:00"; docker compose up --build -d --wait`
> - Linux / macOS: `REMINDER_LEAD=00:01:00 docker compose up --build -d --wait`
> - или строка `REMINDER_LEAD=00:01:00` в файле `.env`.

## Локальный запуск

Команды одинаковы для Windows (PowerShell), Linux и macOS; выполняются в корне репозитория.

```sh
docker compose up --build -d --wait
```

- `--build` собирает образ backend, `-d` запускает в фоне, `--wait` ждёт, пока сервисы пройдут проверку готовности.
- При старте backend сам применяет миграции БД и создаёт демо-аккаунты (повторный старт ничего не дублирует).

После запуска:

| Адрес | Что там |
|---|---|
| http://localhost:8000/docs | Интерактивная документация API (Swagger UI) — можно вызывать запросы из браузера |
| http://localhost:8000/api/health | Проверка работоспособности: `{"status":"ok","database":"ok",...}` |

Полезные команды:

```sh
docker compose logs -f backend                 # журнал backend
docker compose exec db psql -U contest         # консоль PostgreSQL
docker compose down                            # остановить (данные сохраняются)
docker compose down -v                         # остановить и удалить данные БД
```

## Запуск тестов

```sh
docker compose --profile test run --rm --build tests
```

Что запускается: контейнер `tests` (тот же код backend + pytest) и, при необходимости, контейнер `db`. Тесты:

- создают **отдельную** БД `contest_test` (рабочая БД `contest` не затрагивается), применяют к ней миграции Alembic;
- выполняют все тесты backend из [backend/tests](backend/tests) на настоящем PostgreSQL; время управляется в тестах «искусственными часами»;
- проверяют, что схема после миграций совпадает с моделями.

Ожидаемый итог — строка `N passed`. Список тестов этапа 1 — [docs/REQUIREMENTS.md](docs/REQUIREMENTS.md).

## API (текущее состояние)

Полное описание с примерами — http://localhost:8000/docs. Все адреса, кроме входа и health, требуют заголовок `Authorization: Bearer <токен>`.

| Метод и адрес | Кто | Что делает |
|---|---|---|
| `POST /api/auth/login` | все | вход, возвращает токен |
| `POST /api/auth/logout` | вошедший | выход (только эта сессия) |
| `GET /api/auth/me` | вошедший | текущий пользователь |
| `GET /api/users` | организатор | сотрудники — для выбора участников |
| `POST /api/contests` | организатор | создать конкурс: тема, два срока (с часовым поясом), `participant_ids` (не передан — все сотрудники), `client_request_id` |
| `GET /api/contests` | вошедший | конкурсы: организатору все, сотруднику — где он участник |
| `GET /api/contests/{id}` | организатор, участник | снимок конкурса: фаза, `revision`, `server_time`, видимые идеи, статистика (организатору) |
| `POST /api/contests/{id}/ideas` | участник | подать идею (только во время подачи) |
| `PUT /api/ideas/{id}` | автор | изменить идею (только во время подачи; нужен `version`) |
| `DELETE /api/ideas/{id}` | автор | удалить идею (во время подачи и голосования) вместе с голосами за неё |
| `POST /api/ideas/{id}/vote` | участник | проголосовать за чужую идею (только во время голосования); повтор — без второго голоса |
| `DELETE /api/ideas/{id}/vote` | участник | отозвать свой голос (только во время голосования); повтор — без ошибки |
| `WS /api/ws` | вошедший | сигналы реального времени (см. ниже) |
| `GET /api/emails` | вошедший | почтовая заглушка: участнику — его письма, организатору — журнал всех писем; фильтр `contest_id` |

Фаза определяется серверным временем: подача — до срока приёма идей, голосование — до срока голосования, затем финал. Ровно в момент срока раунд уже закрыт ([D-007](docs/DECISIONS.md)). Что видно в каждой фазе:

| Фаза | Участник | Организатор |
|---|---|---|
| подача | только свои идеи | только статистика (участники, идеи) |
| голосование | все идеи без авторов и без счёта, в порядке подачи; свои помечены `is_mine`, свои голоса — `voted_by_me` | все идеи без авторов, **текущий счёт** в порядке результатов + статистика (идеи, проголосовавшие люди, голоса) |
| финал | все идеи с авторами, счётом и победителем (`winner_idea_id`) | то же + статистика |

Кто за какую идею голосовал, API не сообщает никому ([D-036](docs/DECISIONS.md)).

**Правило победителя:** больше голосов → при равенстве раньше поданная идея (правка не меняет время подачи) → при одинаковом времени меньший номер идеи. Если голосов нет — побеждает самая ранняя идея; если идей нет — победителя нет ([D-008](docs/DECISIONS.md)).

Сотрудник, не включённый в конкурс, получает 404 — как будто конкурса нет.

## Реальное время (WebSocket)

Подробно — [D-039](docs/DECISIONS.md) и [D-040](docs/DECISIONS.md).

1. Клиент открывает `ws://localhost:8000/api/ws` и **первым сообщением** присылает `{"type": "auth", "token": "…"}`. Ответ — `{"type": "ready", …}`. Без входа за 5 секунд, с неверным сообщением или токеном соединение закрывается (коды `4408`, `4400`, `4401`).
2. Дальше сервер присылает только **сигналы** — без данных конкурса:
   - `{"type": "contest_changed", "contest_id": N, "revision": R}` — что-то изменилось;
   - `{"type": "phase_changed", "contest_id": N, "revision": R}` — наступил срок раунда;
   - `{"type": "contests_changed"}` — появился новый конкурс;
   - `{"type": "mail_changed"}` — пришли письма (получателям и организатору).
3. Получив сигнал, клиент перечитывает снимок `GET /api/contests/{id}` — права проверяются там.

Сигнал получают только те, у кого экран меняется. Подача и правка идеи и голоса видны организатору и самому автору действия (его вкладкам), удаление идеи во время голосования и наступление срока — всем участникам конкурса. Не участникам конкурса сигналы о нём не приходят. Выход закрывает WebSocket этой вкладки.

## Расписание и письма

Подробно — [D-042 … D-046](docs/DECISIONS.md). Раунды закрываются сами: фаза вычисляется по серверному времени, вручную её никто не переключает.

**Что запланировано.** При создании конкурса в той же транзакции создаются три задания в таблице `jobs`:

| Задание | Когда | Кому письмо |
|---|---|---|
| напоминание о подаче | срок подачи − `REMINDER_LEAD` | участникам без единой идеи в конкурсе (удалившие все идеи — тоже) |
| напоминание о голосовании | срок голосования − `REMINDER_LEAD` | участникам без действующего голоса, если есть чужая идея, за которую можно проголосовать (отозвавшие все голоса — тоже) |
| финал | срок голосования | каждому участнику — одно итоговое письмо с результатами и авторами; автору победившей идеи — то же одно письмо в варианте «ваша идея победила» |

Организатор и сотрудники вне списка участников писем не получают. Каждое напоминание — не больше одного на человека и раунд; повтор исключён ограничением БД.

**Перед отправкой всё проверяется заново:** раунд ещё открыт? участвовал ли человек к этому моменту? Письма и отметка «выполнено» записываются в одной транзакции.

**Короткий конкурс.** Если раунд короче `REMINDER_LEAD` (например, подача длится 3 часа при напоминании за сутки), напоминание этого раунда не отправляется: задание сразу получает статус `skipped` с пояснением «раунд короче срока напоминания». Финал выполняется всегда.

**Простой сервера.** Задания хранятся в PostgreSQL, поэтому после перезапуска обработчик выполняет всё просроченное:
- напоминание — только если его раунд ещё открыт, иначе `skipped` «раунд уже закрыт»;
- финал — с опозданием. Результаты видны с момента срока, письма придут после запуска.

Уже выполненные задания не повторяются.

**Почта — заглушка.** Письмо — строка в таблице `emails`: получатель, адрес, тема, текст, время. Посмотреть — `GET /api/emails` (на этапе 6 — страница «Почта»). Реальная отправка, доставка и адреса **не проверяются**. Время в письмах указано в UTC.

**Ограничения.** Обработчик работает внутри процесса backend. Несколько копий безопасны (`SKIP LOCKED`), но основной сценарий — один процесс. Неудачное задание повторяется до 5 раз с паузой, затем получает статус `failed` с текстом ошибки (видно в таблице `jobs`).

## Проверка API вручную (этапы 1–5)

1. Откройте http://localhost:8000/docs.
2. `POST /api/auth/login` → **Try it out** → тело `{"login": "anna", "password": "demo-password"}` → **Execute**. В ответе — `token` и данные пользователя.
3. Нажмите **Authorize** (замок вверху), вставьте токен, **Authorize**.
4. `GET /api/auth/me` → **Execute** → в ответе `anna`, роль `employee`.
5. Повторите вход с неверным паролем → `401 Неверный логин или пароль`.
6. `POST /api/auth/logout` → `204`; снова `GET /api/auth/me` → `401 Требуется вход`.

Конкурсы и идеи (Swagger запоминает один токен, поэтому для смены пользователя нажмите **Authorize → Logout** и вставьте другой токен):

7. Войдите как `organizer`, авторизуйтесь его токеном. `POST /api/contests`, тело (сроки — на несколько минут вперёд, в UTC с `Z`):
   ```json
   {"topic": "Проверка", "submission_deadline": "2026-11-01T10:05:00Z",
    "voting_deadline": "2026-11-01T10:10:00Z",
    "client_request_id": "3fa85f64-5717-4562-b3fc-2c963f66afa6"}
   ```
   Повторите тот же запрос — вернётся тот же конкурс с кодом `200`, а не новый.
8. Войдите как `anna`, подайте идею: `POST /api/contests/{id}/ideas` с `title`, `description` и новым `client_request_id`. Сделайте то же под `boris`.
9. `GET /api/contests/{id}` под `anna` — только её идея; под `organizer` — пустой список идей и `stats.ideas_count = 2`.
10. Дождитесь срока приёма идей: под `anna` видны обе идеи без авторов; подать или изменить идею — `409 Приём идей закрыт`.
11. После срока голосования — видны авторы.

Голосование (сроки конкурса — 3 и 6 минут вперёд, чтобы успеть):

12. Подайте идеи под `anna` и `boris`. Дождитесь начала голосования.
13. Под `boris` — `POST /api/ideas/{id идеи Анны}/vote` → `201`; повторите → `200`, голос один. За свою идею → `403`.
14. Под `organizer` — `GET /api/contests/{id}`: у идей есть `votes_count`, в `stats` — `voters_count`. Под `vera` счёта нет (`votes_count: null`).
15. Под `boris` — `DELETE /api/ideas/{id}/vote` → `204`; повторите → `204`. У организатора счёт уменьшился.
16. Под `anna` удалите свою идею, за которую голосовали: у организатора уменьшатся `ideas_count`, `votes_count` и, если у голосовавших не осталось голосов, `voters_count`.
17. После срока голосования голосовать и отзывать голос нельзя (`409`); у всех виден `winner_idea_id`.

Реальное время — через консоль браузера (интерфейса пока нет):

18. Откройте две вкладки с http://localhost:8000/docs и в каждой — консоль разработчика (**F12 → Console**). В первой войдите как `organizer`, во второй как `boris` (п. 2) и скопируйте токены.
19. В каждой вкладке выполните, подставив свой токен:
    ```js
    const ws = new WebSocket("ws://localhost:8000/api/ws");
    ws.onmessage = (e) => console.log(new Date().toLocaleTimeString(), e.data);
    ws.onclose = (e) => console.log("закрыто, код", e.code);
    ws.onopen = () => ws.send(JSON.stringify({ type: "auth", token: "ТОКЕН" }));
    ```
    В консоли появится `{"type":"ready",…}`.
20. Создайте конкурс под `organizer` (сроки 2 и 4 минуты вперёд) — в обеих консолях `contests_changed`. Подайте идею под `anna` — сигнал `contest_changed` придёт организатору, а `boris` — нет: чужие идеи во время подачи ему не видны.
21. В момент срока приёма идей в обеих консолях появится `phase_changed` — без перезагрузки и без действий пользователя. Проголосуйте под `boris` — сигнал придёт организатору и `boris`.
22. Выйдите под `boris` (`POST /api/auth/logout`) — в его консоли `закрыто, код 4401`.

Расписание и письма — запустите сервис с напоминанием за минуту (см. «Переменные окружения»; **только для демонстрации**):

23. Под `organizer` создайте конкурс со сроками **через 3 и 5 минут**, участники — `anna`, `boris`, `vera` (`participant_ids` из `GET /api/users`).
24. Сразу подайте идею под `anna`.
25. Через 2 минуты (срок подачи − 1 минута) — `GET /api/emails` под `boris` и `vera`: у каждого напоминание о подаче. У `anna` писем нет: она уже подала идею.
26. После срока подачи проголосуйте под `boris` за идею Анны. Через 4 минуты после создания напоминание о голосовании придёт только `vera`. `anna` не получит его: в конкурсе только её идея, голосовать ей не за что.
27. После срока голосования у всех троих итоговое письмо, у `anna` — «Ваша идея победила». Под `organizer` `GET /api/emails` показывает журнал всех писем.
28. В DBeaver: `select kind, status, run_at, finished_at, note from jobs where contest_id = …;` — у каждого задания статус и пояснение (например, «писем: 2»).
29. Простой: создайте ещё конкурс, выполните `docker compose stop backend` до момента напоминания и `docker compose start backend` после него, пока подача ещё идёт. Напоминание придёт сразу после запуска; если же подача успела закрыться — задание получит `skipped` «раунд уже закрыт».

## Проверка двумя клиентами

Вход хранится в `sessionStorage` — у каждой вкладки браузера свой вход ([D-003](docs/DECISIONS.md)):

- **Две вкладки разных пользователей** (например, участник и организатор): войдите в каждой вкладке под своим логином; вход во второй вкладке не меняет пользователя в первой.
- **Две вкладки одного пользователя**: войдите в обеих (или используйте «Дублировать вкладку» — дубликат сохраняет вход). Выход в одной вкладке не завершает сессию другой.
- **Компромисс:** новая вкладка требует повторного входа; токен доступен JavaScript страницы (при XSS-уязвимости его можно похитить), поэтому для продакшена правильнее HttpOnly-cookie с защитой от CSRF.

На этапе 1 это поведение проверено на уровне API (`test_two_tabs_*` в [backend/tests/test_auth.py](backend/tests/test_auth.py)), на этапе 4 — для WebSocket: у каждой вкладки своё соединение, выход закрывает только его ([backend/tests/test_realtime.py](backend/tests/test_realtime.py)). Сценарии в интерфейсе появятся на этапах 6–7.

| Голоса, отзыв, результаты, победитель, статистика организатора | работают через API, покрыты тестами (в т. ч. параллельные запросы) |
| WebSocket: сигналы об изменениях и о сроках | работает, покрыт тестами с настоящим сервером и независимыми соединениями |
| Расписание: напоминания, финал, итоговые письма, почтовая заглушка | работают, покрыты тестами (получатели, повторы, простой, перезапуск, параллельные обработчики, ошибки); проверено вживую |
| Frontend | не начато (этап 6) |

Сознательно не делаем: регистрацию, OAuth, восстановление пароля, реальную отправку почты, LLM-функции (не требуются заданием).

## Что улучшить следующим шагом

- Ограничение частоты попыток входа (сейчас нет защиты от перебора паролей).
- Повторная подача с `client_request_id` уже удалённой идеи создаёт её заново (идея удаляется физически); при необходимости — хранить использованные идентификаторы отдельно.
- Очистка истёкших сессий (сейчас они только перестают действовать).
- Полная блокировка версий транзитивных зависимостей Python ([D-019](docs/DECISIONS.md)).
