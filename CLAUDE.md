Полный исходный промпт — [docs/PROMPTS.md](docs/PROMPTS.md), запись 1. Здесь сжатая выжимка.

## Начало каждой сессии
1. Прочитать этот файл, [docs/PLAN.md](docs/PLAN.md) и последние записи [docs/DEVELOPMENT_LOG.md](docs/DEVELOPMENT_LOG.md).
2. Коротко сообщить пользователю, на каком этапе работа и что дальше.
3. Ничего не делать до команды пользователя.

## Порядок работы
- Работа идёт по этапам из docs/PLAN.md. Выполнять **только один согласованный этап за раз**. Разрешение на один этап не распространяется на следующие.
- Внутри этапа действовать самостоятельно: реализовать, запускать проверки, исправлять ошибки.
- Существенное изменение архитектуры или объёма этапа — сначала объяснить причину и получить согласие.
- После каждого этапа: что изменилось и зачем; какие проверки запущены и их **фактический** результат; короткий сценарий ручной проверки; оставшиеся проблемы; обновить DEVELOPMENT_LOG, PLAN, REQUIREMENTS (и README при необходимости); **остановиться и ждать команды**.
- Последний этап — приёмка: свежий клон в отдельную папку, запуск строго по README, все тесты, проход по docs/REQUIREMENTS.md.
- Не называть проверку пройденной, если она не запускалась. Если запуск невозможен — указать причину и точную инструкцию.

## Продукт и стек
- Реализуем только «Задание 7. Конкурс идей» + разделы «Требования» и «Что мы ожидаем от вас». Текст задания — `assignment.md` в корне (в .gitignore, в Git не добавлять; папку `task/` тоже).
- Стек выбран пользователем: FastAPI, PostgreSQL, Vue 3 + Vite (**JavaScript**, не TypeScript), Docker Compose. Менять стек — только с обоснованием до реализации.
- Минимально достаточная архитектура. Redis/Kafka/Celery/микросервисы — только при конкретной необходимости и после объяснения. Никаких LLM-функций и возможностей вне задания.
- **Каждая библиотека и каждое существенное решение** — запись в docs/DECISIONS.md (что, альтернативы, почему) **до** добавления зависимости.
- Причины выбора, которые принадлежат пользователю (стек, инструмент, модель), записывать **с его слов**, не придумывать.
- Основной запуск — Docker Compose. Локальный Node.js пользователя (18.x) не обновляем; frontend собирается и тестируется в Docker.
- Инструкции — кроссплатформенные (Windows / Linux / macOS) или с вариантами для каждой ОС.

## Ключевые продуктовые правила (детали — docs/DECISIONS.md)
- Серверное время определяет фазу; ровно в момент срока раунд закрыт. Проверки прав, сроков и допустимости — на сервере.
- Голос: уникальность пары (участник, идея) ограничением БД; можно голосовать за несколько чужих идей; за свою — нельзя.
- Несколько идей от участника; защита от повторной отправки через `client_request_id`.
- Ничья: больше голосов → раньше `submitted_at` → меньше `id`. Если идеи есть, но голосов нет — побеждает самая ранняя идея; если идей нет — победителя нет.
- Организатор не подаёт идеи, не голосует, не видит авторов до финала.
- Вход: токен в `sessionStorage`, отдельный вход в каждой вкладке.
- Почта — таблица в PostgreSQL + страница просмотра; участник видит только свои письма.
- WS-события — сигналы без чувствительных данных; клиент перечитывает снимок через REST; защита от устаревших данных через `revision`.

## Тесты
- Содержательные тесты в каждом этапе. Транзакции и конкурентность — на PostgreSQL, параллельные запросы — через независимые соединения.
- Время в тестах — управляемые часы. Журнал разработки — только реальное время.
- Браузерные E2E для ключевых сценариев с независимыми сессиями.
- Все проверки — одной документированной командой (через Docker).

- Поддерживать: README.md, docs/REQUIREMENTS.md, docs/DECISIONS.md, docs/DEVELOPMENT_LOG.md, docs/PROMPTS.md, docs/AI_USAGE.md, docs/PLAN.md.
- В docs/PROMPTS.md добавлять существенные команды и уточнения пользователя с временными отметками.
- Локальные коммиты после законченных и проверенных частей. Не подделывать даты, не переписывать историю ради видимости.
