## D-001. Базовый стек — принято

- **Выбрано:** backend — Python + FastAPI; БД — PostgreSQL; frontend — Vue 3 + Vite; локальный запуск — Docker Compose.
- **Альтернативы (из задания):** Go, Node.js для backend; React для frontend; MySQL и другие реляционные СУБД.
- **Причины (со слов пользователя, запись 2 в PROMPTS.md):** «FastAPI и PostgreSQL, потому что есть опыт с ними. Vue 3 и Vite для отдельного фронта, эту часть буду осваивать по ходу проекта. docker compose для локального запуска».

## D-002. Frontend на JavaScript — принято

- **Выбрано:** JavaScript (без TypeScript).
- **Альтернатива:** TypeScript — типизированный контракт данных, но дополнительный слой для изучения.
- **Причина:** решение пользователя (запись 2). Чтобы компенсировать отсутствие типов, формы данных API описываются в README/коде комментариями, а корректность обеспечивается backend-валидацией (Pydantic) и тестами.

## D-003. Модель входа: логин и пароль, токен в sessionStorage — принято

- **Выбрано:** заранее созданные демо-аккаунты с логином и паролем (хеш пароля в БД). Сервер выдаёт непрозрачный случайный токен и хранит только его хеш в таблице `sessions`. Клиент хранит токен в `sessionStorage` — хранилище браузера, своё у каждой вкладки — и отправляет его в заголовке `Authorization: Bearer …`; для WebSocket — первым сообщением после подключения. Пользователь и роль определяются только по сессии на сервере.
- **Альтернативы:**
  - *HttpOnly-cookie.* Защищена от чтения JavaScript (лучше при XSS), но cookie общие для всех вкладок браузера: вход во второй вкладке незаметно подменяет пользователя в первой. Для сценария «участник и организатор в двух вкладках» потребовались бы разные профили браузера или режим инкогнито.
  - *JWT без хранения на сервере.* Нельзя отозвать сессию при выходе; для задачи без нескольких сервисов преимуществ нет.
  - *Без входа, выбор пользователя из списка.* Сервер доверял бы идентичности, присланной клиентом, — запрещено требованиями.
- **Почему:** проверяющий, скорее всего, откроет две вкладки одного браузера; с `sessionStorage` в них можно войти под разными пользователями, и пользователь вкладки не меняется без её ведома. Решение пользователя (запись 2): «оставляем токен в sessionStorage и отдельный вход в каждой вкладке».
- **Компромиссы и ограничения (будут описаны в README):**
  - Новая вкладка требует нового входа. Команда браузера «Дублировать вкладку» копирует sessionStorage, поэтому дубликат остаётся под тем же пользователем.
  - Закрытие вкладки «забывает» вход; серверная сессия остаётся до истечения срока или выхода.
  - Токен доступен JavaScript страницы: при XSS-уязвимости его можно похитить. Снижаем риск тем, что Vue экранирует выводимый текст, а пользовательский HTML не вставляется. Для продакшена правильнее HttpOnly-cookie с отдельной защитой от CSRF.
  - Две вкладки **одного** пользователя — две независимые сессии; действия в одной отражаются в другой через WebSocket.

## D-004. Публичный демо-пароль — принято

- **Выбрано:** у демо-аккаунтов общий публичный пароль, указанный в README и сид-данных. Это синтетическое значение, а не секрет.
- **Альтернатива:** задавать пароль только через `.env`.
- **Почему:** проверяющему проще запуститься; согласовано пользователем (запись 2). Настоящих секретов в репозитории нет.

## D-005. Роль организатора — принято

- **Выбрано:** глобальная роль пользователя `organizer` / `employee`. Организатор создаёт конкурсы и видит экран организатора; **не подаёт идеи, не голосует, не видит авторов до финала**. Счёт голосов и тексты идей видит с начала голосования; во время подачи — только число идей и число участников.
- **Альтернативы:** организатор как обычный участник своего конкурса; организатор видит авторов во время голосования.
- **Почему:** организатор видит живые результаты — участие давало бы ему преимущество; задание говорит о голосовании «без авторов» без исключений. Согласовано пользователем (запись 2).

## D-006. Несколько идей от участника, защита от повторной отправки — принято

- **Выбрано:** участник может подать несколько идей. Форма при открытии получает `client_request_id` (UUID); ограничение БД `UNIQUE(author_id, client_request_id)`. Повторная отправка той же формы (двойное нажатие, повтор запроса) возвращает уже созданную идею, а не новую.
- **Альтернатива:** одна идея на участника (`UNIQUE(contest_id, author_id)`).
- **Почему:** формулировка «один голос на идею от человека» предполагает много идей; решение пользователя (запись 2).

## D-007. Фазы и границы времени — принято

- **Выбрано:** фаза вычисляется по серверному времени при каждом запросе:
  - подача — `now < submission_deadline`;
  - голосование — `submission_deadline ≤ now < voting_deadline`;
  - финал — `now ≥ voting_deadline`.
  Ровно в момент срока раунд уже закрыт. Фаза не зависит от того, успел ли сработать фоновый обработчик. Приём идей открывается в момент создания конкурса.
- При создании проверяется `now < submission_deadline < voting_deadline`. **Сроки после создания не меняются.**
- Источник времени — объект `Clock` в backend; в тестах подменяется управляемыми часами. Время хранится в `timestamptz`, показывается в часовом поясе браузера.
- **Альтернативы:** статус фазы в БД, переключаемый фоновым обработчиком (задержка обработчика разрешала бы просроченные операции); изменяемые сроки (усложняет расписание и напоминания).

## D-008. Победитель и ничья — принято

- **Выбрано:** порядок результатов: больше голосов → раньше `submitted_at` → меньше `id` (устойчивый порядок при одинаковых отметках времени). `submitted_at` задаётся при первой подаче и при правке не меняется.
- Если идеи есть, но голосов нет — правило ничьей применяется буквально: побеждает самая ранняя идея. Если идей нет — победителя нет.
- Правило показывается на странице конкурса с начала подачи.
- **Альтернатива:** не объявлять победителя при нуле голосов (было предложено агентом).
- **Почему:** решение пользователя (запись 2): правило из задания применяется без исключений.

## D-009. Список участников конкурса — принято

- **Выбрано:** таблица `contest_participants (contest_id, user_id)`. При создании конкурса организатор отмечает сотрудников; по умолчанию отмечены все. Подавать идеи, голосовать, видеть конкурс и получать письма могут только участники из списка.
- **Альтернатива:** «все сотрудники компании» без явного списка — тогда состав получателей писем зависит от момента рассылки.
- **Почему:** напоминания и итоговое письмо требуют известного списка, включая тех, кто ничего не сделал.

## D-010. Участие в раунде (для напоминаний) — принято

- **Выбрано:** участие определяется по **текущему состоянию в момент отправки напоминания**:
  - участвовал в подаче — есть хотя бы одна неудалённая идея в конкурсе;
  - участвовал в голосовании — есть хотя бы один действующий голос в конкурсе.
  Отозвал все голоса или удалил все идеи — считается неучаствовавшим. Голос, исчезнувший вместе с удалённой идеей, тоже не считается.
- Не более **одного** напоминания на получателя на раунд, независимо от последующих изменений.
- **Альтернатива:** «участвовал когда-либо» (хранить историю действий).
- **Почему:** напоминание адресовано тем, чьего вклада в раунде сейчас нет; правило совпадает с подсчётом «проголосовавших людей» и проверяемо одним запросом.

## D-011. Удаление идей — принято

- **Выбрано:** автор может удалить свою идею во время подачи (голосов ещё нет) и во время голосования (вместе с голосами, атомарно). После финала удаление запрещено — результаты зафиксированы.
- **Альтернатива:** разрешить удаление только во время голосования, как буквально описано в задании.

## D-012. Итоговые письма — принято

- **Выбрано:** после финала каждый из списка участников получает одно итоговое письмо; автор победившей идеи получает **то же одно письмо** в варианте «вы победили». Дубли исключает `UNIQUE(contest_id, recipient_user_id, kind)`. Если идей нет — письмо «конкурс завершён, идей не подано».
- **Альтернатива:** два отдельных письма победителю (итог и поздравление).

## D-013. Конкурентный доступ — принято

- **Выбрано:**
  - голос: первичный ключ `(idea_id, voter_id)`; добавление через `INSERT … ON CONFLICT DO NOTHING` — повтор возвращает тот же итог; отзыв повторно — тоже успех без изменений;
  - `votes.idea_id → ideas.id ON DELETE CASCADE`: голоса удаляются в той же транзакции, что и идея;
  - у конкурса счётчик `revision`; каждая изменяющая транзакция выполняет `UPDATE contests SET revision = revision + 1` — эта блокировка строки выстраивает изменения одного конкурса в очередь, поэтому голос и удаление той же идеи не перемешиваются: либо голос удаляется вместе с идеей, либо голосу отвечают 404 «идея удалена»;
  - правка идеи — с полем `version`; при устаревшей версии — 409 и актуальные данные.
- **Альтернативы:** уровень изоляции SERIALIZABLE с повторами транзакций; проверка уникальности в коде без ограничения БД (ненадёжно при параллельных запросах).
- **Почему:** ограничения БД и блокировка одной строки дают гарантии, которые просто объяснить и проверить тестами на PostgreSQL.

## D-014. Обновления в реальном времени — принято

- **Выбрано:** встроенный WebSocket FastAPI; менеджер соединений в памяти процесса. Событие — сигнал без чувствительных данных: `{type, contest_id, revision}`. Клиент по сигналу перечитывает снимок через REST, где проверяются права. Публикация — только после успешного коммита. Клиент переподключается с нарастающей задержкой и сразу перечитывает снимок; ответы и события с `revision` меньше уже применённого отбрасываются.
- **Альтернативы:** отправлять данные прямо в событии (нужна отдельная фильтрация по ролям в каждом сообщении — риск утечки авторов и счёта); Server-Sent Events; опрос; PostgreSQL LISTEN/NOTIFY или Redis pub/sub для нескольких процессов.
- **Почему:** права проверяются в одном месте (REST), утечка через WS исключена конструктивно.
- **Ограничение:** работает в одном процессе backend. Для нескольких процессов нужен LISTEN/NOTIFY — следующий шаг.

## D-015. Расписание — принято

- **Выбрано:** таблица `jobs` в PostgreSQL. При создании конкурса создаются задания `remind_submission`, `remind_voting`, `finalize` с моментом запуска. Фоновый цикл asyncio в процессе backend раз в несколько секунд забирает наступившие задания через `SELECT … FOR UPDATE SKIP LOCKED`, заново проверяет фазу и участие, создаёт письма и помечает задание выполненным — в одной транзакции. Ограничение `UNIQUE(contest_id, kind)`.
- Срок напоминания — переменная окружения `REMINDER_LEAD` (по умолчанию 24 часа; меньшее значение — только для демонстрации).
- **Раунд короче `REMINDER_LEAD`:** если момент «срок − REMINDER_LEAD» раньше начала раунда, напоминание не отправляется; задание получает статус `skipped` с причиной.
- **Простой сервера:** после запуска просроченные напоминания отправляются, только если раунд ещё открыт (участие проверяется заново), иначе `skipped`; просроченный финал выполняется с опозданием. Результаты видны с момента срока независимо от обработчика.
- **Альтернативы:** APScheduler с хранилищем в БД; Celery + Redis (лишние компоненты для одного процесса).
- **Ограничение:** обработчик живёт в процессе backend; `SKIP LOCKED` делает безопасным запуск нескольких копий, но это не основной сценарий.

## D-016. Почтовая заглушка — принято

- **Выбрано:** таблица `emails` в PostgreSQL (получатель, тема, текст, время, тип) и страница просмотра. Обычный участник видит только свои письма; организатор видит журнал всех писем — это удобно для проверки рассылки (подтверждено пользователем, запись 3). Письмо создаётся в той же транзакции, что и отметка о выполнении задания.
- **Альтернатива:** Mailpit (SMTP + веб-интерфейс) — отдельный контейнер; при сбое между отправкой и коммитом возможен дубль.
- **Почему:** «ровно одно письмо» гарантируется транзакцией и проверяется тестами; решение пользователя (запись 2).
- **Ограничение:** реальная доставка не выполняется и не проверяется.

## D-017. Node.js на машине разработчика — принято

- **Выбрано:** локальный Node.js (18.x) не обновляем; сборка и тесты frontend выполняются в Docker-контейнерах. Если понадобится локальная разработка frontend, совместимая версия выбирается отдельно.
- **Почему:** решение пользователя (запись 2).

## D-018. Окончания строк — реализовано (этап 0)

- **Выбрано:** `.gitattributes` с `* text=auto eol=lf` и явными правилами для `*.sh`, `Dockerfile*`, `*.yml`.
- **Альтернатива:** полагаться на `core.autocrlf` — зависит от настроек конкретной машины; на Windows с `autocrlf=true` shell-скрипты получили бы CRLF и сломались бы в Linux-контейнере.
