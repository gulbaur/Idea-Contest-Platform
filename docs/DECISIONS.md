## D-001. Базовый стек — принято

- **Выбрано:** backend — Python + FastAPI; БД — PostgreSQL; frontend — Vue 3 + Vite; локальный запуск — Docker Compose.
- **Альтернативы (из задания):** Go, Node.js для backend; React для frontend; MySQL и другие реляционные СУБД.
- **Причины (со слов пользователя, запись 2 в PROMPTS.md):** «FastAPI и PostgreSQL, потому что есть опыт с ними. Vue 3 и Vite для отдельного фронта, эту часть буду осваивать по ходу проекта. docker compose для локального запуска».

## D-002. Frontend на JavaScript — принято

- **Выбрано:** JavaScript (без TypeScript).
- **Альтернатива:** TypeScript — типизированный контракт данных, но дополнительный слой для изучения.

## D-003. Модель входа: логин и пароль, токен в sessionStorage — принято

- **Выбрано:** заранее созданные демо-аккаунты с логином и паролем (хеш пароля в БД). Сервер выдаёт непрозрачный случайный токен и хранит только его хеш в таблице `sessions`. Клиент хранит токен в `sessionStorage` — хранилище браузера, своё у каждой вкладки — и отправляет его в заголовке `Authorization: Bearer …`; для WebSocket — первым сообщением после подключения. Пользователь и роль определяются только по сессии на сервере.
- **Альтернативы:**
  - *HttpOnly-cookie.* Защищена от чтения JavaScript (лучше при XSS), но cookie общие для всех вкладок браузера: вход во второй вкладке незаметно подменяет пользователя в первой. Для сценария «участник и организатор в двух вкладках» потребовались бы разные профили браузера или режим инкогнито.
  - *JWT без хранения на сервере.* Нельзя отозвать сессию при выходе; для задачи без нескольких сервисов преимуществ нет.
  - *Без входа, выбор пользователя из списка.* Сервер доверял бы идентичности, присланной клиентом, — запрещено требованиями.
- **Почему:** проверяющий, скорее всего, откроет две вкладки одного браузера; с `sessionStorage` в них можно войти под разными пользователями, и пользователь вкладки не меняется без её ведома. Решение пользователя (запись 2): «оставляем токен в sessionStorage и отдельный вход в каждой вкладке».
- **Компромиссы и ограничения (будут описаны в README):**
  - Новая вкладка требует нового входа. Команда браузера «Дублировать вкладку» копирует sessionStorage, поэтому дубликат остаётся под тем же пользователем.
  - Закрытие вкладки «забывает» вход; серверная сессия остаётся до истечения срока или выхода.
  - Токен доступен JavaScript страницы: при XSS-уязвимости его можно похитить. Снижаем риск тем, что Vue экранирует выводимый текст, а пользовательский HTML не вставляется. Для продакшена правильнее HttpOnly-cookie с отдельной защитой от CSRF.
  - Две вкладки **одного** пользователя — две независимые сессии; действия в одной отражаются в другой через WebSocket.

## D-004. Публичный демо-пароль — принято

- **Выбрано:** у демо-аккаунтов общий публичный пароль, указанный в README и сид-данных. Это синтетическое значение, а не секрет.
- **Альтернатива:** задавать пароль только через `.env`.
- **Почему:** проверяющему проще запуститься; согласовано пользователем (запись 2). Настоящих секретов в репозитории нет.

## D-005. Роль организатора — принято

- **Выбрано:** глобальная роль пользователя `organizer` / `employee`. Организатор создаёт конкурсы и видит экран организатора; **не подаёт идеи, не голосует, не видит авторов до финала**. Счёт голосов и тексты идей видит с начала голосования; во время подачи — только число идей и число участников.
- **Альтернативы:** организатор как обычный участник своего конкурса; организатор видит авторов во время голосования.
- **Почему:** организатор видит живые результаты — участие давало бы ему преимущество; задание говорит о голосовании «без авторов» без исключений. Согласовано пользователем (запись 2).

## D-006. Несколько идей от участника, защита от повторной отправки — принято

- **Выбрано:** участник может подать несколько идей. Форма при открытии получает `client_request_id` (UUID); ограничение БД `UNIQUE(author_id, client_request_id)`. Повторная отправка той же формы (двойное нажатие, повтор запроса) возвращает уже созданную идею, а не новую.
- **Альтернатива:** одна идея на участника (`UNIQUE(contest_id, author_id)`).
- **Почему:** формулировка «один голос на идею от человека» предполагает много идей; решение пользователя (запись 2).

## D-007. Фазы и границы времени — принято

- **Выбрано:** фаза вычисляется по серверному времени при каждом запросе:
  - подача — `now < submission_deadline`;
  - голосование — `submission_deadline ≤ now < voting_deadline`;
  - финал — `now ≥ voting_deadline`.
  Ровно в момент срока раунд уже закрыт. Фаза не зависит от того, успел ли сработать фоновый обработчик. Приём идей открывается в момент создания конкурса.
- При создании проверяется `now < submission_deadline < voting_deadline`. **Сроки после создания не меняются.**
- Источник времени — объект `Clock` в backend; в тестах подменяется управляемыми часами. Время хранится в `timestamptz`, показывается в часовом поясе браузера.
- **Альтернативы:** статус фазы в БД, переключаемый фоновым обработчиком (задержка обработчика разрешала бы просроченные операции); изменяемые сроки (усложняет расписание и напоминания).

## D-008. Победитель и ничья — принято

- **Выбрано:** порядок результатов: больше голосов → раньше `submitted_at` → меньше `id` (устойчивый порядок при одинаковых отметках времени). `submitted_at` задаётся при первой подаче и при правке не меняется.
- Если идеи есть, но голосов нет — правило ничьей применяется буквально: побеждает самая ранняя идея. Если идей нет — победителя нет.
- Правило показывается на странице конкурса с начала подачи.
- **Альтернатива:** не объявлять победителя при нуле голосов (было предложено агентом).
- **Почему:** решение пользователя (запись 2): правило из задания применяется без исключений.

## D-009. Список участников конкурса — принято

- **Выбрано:** таблица `contest_participants (contest_id, user_id)`. При создании конкурса организатор отмечает сотрудников; по умолчанию отмечены все. Подавать идеи, голосовать, видеть конкурс и получать письма могут только участники из списка.
- **Альтернатива:** «все сотрудники компании» без явного списка — тогда состав получателей писем зависит от момента рассылки.
- **Почему:** напоминания и итоговое письмо требуют известного списка, включая тех, кто ничего не сделал.

## D-010. Участие в раунде (для напоминаний) — реализовано (этап 5, D-044)

- **Выбрано:** участие определяется по **текущему состоянию в момент отправки напоминания**:
  - участвовал в подаче — есть хотя бы одна неудалённая идея в конкурсе;
  - участвовал в голосовании — есть хотя бы один действующий голос в конкурсе.
  Отозвал все голоса или удалил все идеи — считается неучаствовавшим. Голос, исчезнувший вместе с удалённой идеей, тоже не считается.
- Не более **одного** напоминания на получателя на раунд, независимо от последующих изменений.
- **Альтернатива:** «участвовал когда-либо» (хранить историю действий).
- **Почему:** напоминание адресовано тем, чьего вклада в раунде сейчас нет; правило совпадает с подсчётом «проголосовавших людей» и проверяемо одним запросом.

## D-011. Удаление идей — принято

- **Выбрано:** автор может удалить свою идею во время подачи (голосов ещё нет) и во время голосования (вместе с голосами, атомарно). После финала удаление запрещено — результаты зафиксированы.
- **Альтернатива:** разрешить удаление только во время голосования, как буквально описано в задании.

## D-012. Итоговые письма — реализовано (этап 5, D-044)

- **Выбрано:** после финала каждый из списка участников получает одно итоговое письмо; автор победившей идеи получает **то же одно письмо** в варианте «вы победили». Дубли исключает `UNIQUE(contest_id, recipient_user_id, kind)`. Если идей нет — письмо «конкурс завершён, идей не подано».
- **Альтернатива:** два отдельных письма победителю (итог и поздравление).

## D-013. Конкурентный доступ — принято

- **Выбрано:**
  - голос: первичный ключ `(idea_id, voter_id)`; добавление через `INSERT … ON CONFLICT DO NOTHING` — повтор возвращает тот же итог; отзыв повторно — тоже успех без изменений;
  - `votes.idea_id → ideas.id ON DELETE CASCADE`: голоса удаляются в той же транзакции, что и идея;
  - у конкурса счётчик `revision`; каждая изменяющая транзакция выполняет `UPDATE contests SET revision = revision + 1` — эта блокировка строки выстраивает изменения одного конкурса в очередь, поэтому голос и удаление той же идеи не перемешиваются: либо голос удаляется вместе с идеей, либо голосу отвечают 404 «идея удалена»;
  - правка идеи — с полем `version`; при устаревшей версии — 409 и актуальные данные.
- **Альтернативы:** уровень изоляции SERIALIZABLE с повторами транзакций; проверка уникальности в коде без ограничения БД (ненадёжно при параллельных запросах).
- **Почему:** ограничения БД и блокировка одной строки дают гарантии, которые просто объяснить и проверить тестами на PostgreSQL.

## D-014. Обновления в реальном времени — принято

- **Выбрано:** встроенный WebSocket FastAPI; менеджер соединений в памяти процесса. Событие — сигнал без чувствительных данных: `{type, contest_id, revision}`. Клиент по сигналу перечитывает снимок через REST, где проверяются права. Публикация — только после успешного коммита. Клиент переподключается с нарастающей задержкой и сразу перечитывает снимок; ответы и события с `revision` меньше уже применённого отбрасываются.
- **Альтернативы:** отправлять данные прямо в событии (нужна отдельная фильтрация по ролям в каждом сообщении — риск утечки авторов и счёта); Server-Sent Events; опрос; PostgreSQL LISTEN/NOTIFY или Redis pub/sub для нескольких процессов.
- **Почему:** права проверяются в одном месте (REST), утечка через WS исключена конструктивно.
- **Ограничение:** работает в одном процессе backend. Для нескольких процессов нужен LISTEN/NOTIFY — следующий шаг.

## D-015. Расписание — реализовано (этап 5, D-042, D-043)

- **Выбрано:** таблица `jobs` в PostgreSQL. При создании конкурса создаются задания `remind_submission`, `remind_voting`, `finalize` с моментом запуска. Фоновый цикл asyncio в процессе backend раз в несколько секунд забирает наступившие задания через `SELECT … FOR UPDATE SKIP LOCKED`, заново проверяет фазу и участие, создаёт письма и помечает задание выполненным — в одной транзакции. Ограничение `UNIQUE(contest_id, kind)`.
- Срок напоминания — переменная окружения `REMINDER_LEAD` (по умолчанию 24 часа; меньшее значение — только для демонстрации).
- **Раунд короче `REMINDER_LEAD`:** если момент «срок − REMINDER_LEAD» раньше начала раунда, напоминание не отправляется; задание получает статус `skipped` с причиной.
- **Простой сервера:** после запуска просроченные напоминания отправляются, только если раунд ещё открыт (участие проверяется заново), иначе `skipped`; просроченный финал выполняется с опозданием. Результаты видны с момента срока независимо от обработчика.
- **Альтернативы:** APScheduler с хранилищем в БД; Celery + Redis (лишние компоненты для одного процесса).
- **Ограничение:** обработчик живёт в процессе backend; `SKIP LOCKED` делает безопасным запуск нескольких копий, но это не основной сценарий.

## D-016. Почтовая заглушка — реализовано (этап 5, D-045)

- **Выбрано:** таблица `emails` в PostgreSQL (получатель, тема, текст, время, тип) и страница просмотра. Обычный участник видит только свои письма; организатор видит журнал всех писем — это удобно для проверки рассылки (подтверждено пользователем, запись 3). Письмо создаётся в той же транзакции, что и отметка о выполнении задания.
- **Альтернатива:** Mailpit (SMTP + веб-интерфейс) — отдельный контейнер; при сбое между отправкой и коммитом возможен дубль.
- **Почему:** «ровно одно письмо» гарантируется транзакцией и проверяется тестами; решение пользователя (запись 2).
- **Ограничение:** реальная доставка не выполняется и не проверяется.

## D-017. Node.js на машине разработчика — принято

- **Выбрано:** локальный Node.js (18.x) не обновляем; сборка и тесты frontend выполняются в Docker-контейнерах. Если понадобится локальная разработка frontend, совместимая версия выбирается отдельно.
- **Почему:** решение пользователя (запись 2).

## D-018. Окончания строк — реализовано (этап 0)

- **Выбрано:** `.gitattributes` с `* text=auto eol=lf` и явными правилами для `*.sh`, `Dockerfile*`, `*.yml`.
- **Альтернатива:** полагаться на `core.autocrlf` — зависит от настроек конкретной машины; на Windows с `autocrlf=true` shell-скрипты получили бы CRLF и сломались бы в Linux-контейнере.

# Этап 1 — каркас backend, БД, вход

## D-019. Управление зависимостями Python — реализовано (этап 1)

- **Выбрано:** `pip` и два файла: `backend/requirements.txt` (рабочие зависимости) и `backend/requirements-dev.txt` (тестовые). Прямые зависимости закреплены точными версиями (`==`), актуальными на 2026-10-30 (проверено установкой в контейнере `python:3.13-slim`).
- **Альтернативы:** Poetry, uv, pip-tools с полной блокировкой транзитивных зависимостей.
- **Почему:** установка выполняется только внутри Docker-образа, отдельный менеджер пакетов не нужен; файлы читаются без подготовки.
- **Ограничение:** транзитивные зависимости не закреплены; при сборке через месяцы они могут обновиться. Полная блокировка (pip-tools / uv lock) — кандидат на улучшение.

## D-020. ORM и драйвер БД: SQLAlchemy 2 (async) + asyncpg — реализовано (этап 1)

- **Выбрано:** `SQLAlchemy[asyncio]==2.1.6` (асинхронный режим), драйвер `asyncpg==0.32.0`.
- **Альтернативы:** SQLModel (надстройка над SQLAlchemy — меньше кода, но меньше контроля над транзакциями и ограничениями); «сырой» asyncpg без ORM (полный контроль SQL, но ручное отображение строк и больше шаблонного кода); psycopg 3 как драйвер.
- **Почему:** FastAPI асинхронный, и async-драйвер не блокирует цикл событий — это важно при одновременной работе WebSocket и фонового обработчика в одном процессе. SQLAlchemy даёт явное управление транзакциями, `INSERT … ON CONFLICT`, `FOR UPDATE SKIP LOCKED` и ограничения БД, которые нужны для D-013 и D-015. asyncpg — самый распространённый async-драйвер PostgreSQL.

## D-021. Миграции: Alembic — реализовано (этап 1)

- **Выбрано:** `alembic==1.20.1`; миграции пишутся вручную и применяются при старте контейнера backend (`alembic upgrade head`). Тест проверяет, что схема после миграций совпадает с моделями (`alembic.autogenerate.compare_metadata`).
- **Альтернативы:** `metadata.create_all()` при старте (нет истории изменений схемы); голые SQL-файлы.
- **Почему:** стандартный инструмент для SQLAlchemy; применение при старте упрощает запуск «одной командой».

## D-022. Конфигурация: pydantic-settings — реализовано (этап 1)

- **Выбрано:** `pydantic-settings==2.16.2` — класс `Settings` читает переменные окружения с типами и значениями по умолчанию.
- **Альтернатива:** `os.environ` вручную.
- **Почему:** проверка типов при старте (например, `REMINDER_LEAD` как длительность), единое место для всех настроек; та же модель Pydantic, что уже знакома пользователю.

## D-023. Хеширование паролей и токены — реализовано (этап 1)

- **Выбрано:** пароли — `hashlib.scrypt` из стандартной библиотеки Python, со случайной солью; хранится строка `scrypt$n$r$p$соль$хеш`; сравнение — `hmac.compare_digest`. Токен сессии — `secrets.token_urlsafe(32)`; в БД хранится только SHA-256 токена. Срок жизни сессии — `SESSION_TTL_HOURS` (по умолчанию 24 часа).
- **Альтернативы:** `pwdlib[argon2]` (рекомендован в документации FastAPI — дополнительная зависимость); `passlib` (не поддерживается); `bcrypt`.
- **Почему:** scrypt — устойчивая к перебору функция из стандартной библиотеки, зависимость не нужна. SHA-256 для токена достаточно: токен случайный и длинный, перебор невозможен; утечка таблицы `sessions` не даёт рабочих токенов.

## D-024. ASGI-сервер: uvicorn — реализовано (этап 1)

- **Выбрано:** `uvicorn[standard]==0.54.0`, один процесс (`--workers` не используется).
- **Альтернативы:** hypercorn, gunicorn с uvicorn-воркерами.
- **Почему:** стандартный сервер для FastAPI; вариант `[standard]` включает библиотеку `websockets` для этапа 4. Один процесс — сознательное решение (D-014, D-015).

## D-025. Тестирование backend: pytest + pytest-asyncio + httpx на реальном PostgreSQL — реализовано (этап 1)

- **Выбрано:** `pytest==9.2.0`, `pytest-asyncio==1.4.1`, `httpx==0.28.1`. Запросы к приложению идут через `httpx.AsyncClient` с `ASGITransport` (без сетевого порта). Тесты работают с отдельной БД `<имя>_test` в том же контейнере PostgreSQL: в начале прогона она пересоздаётся и мигрирует Alembic, перед каждым тестом таблицы очищаются (`TRUNCATE`).
- **Альтернативы:** SQLite в памяти (другая СУБД — не проверяет ограничения и блокировки PostgreSQL); откат транзакции после каждого теста (не подходит для тестов конкурентности, где нужны настоящие коммиты из независимых соединений); testcontainers (ещё одна зависимость; PostgreSQL уже есть в compose); `TestClient` FastAPI (синхронный).
- **Почему:** требования к транзакциям и параллельным запросам проверяются только на настоящем PostgreSQL; очистка через `TRUNCATE` совместима с независимыми соединениями.

## D-026. Источник времени: объект Clock в `app.state` — реализовано (этап 1)

- **Выбрано:** `SystemClock` (UTC) в работе и `FakeClock` с методами `set()` / `advance()` в тестах. Часы хранятся в `app.state.clock`, их используют и HTTP-обработчики, и (с этапа 5) фоновый обработчик. Все отметки времени в БД (`created_at`, `expires_at` и далее `submitted_at`) берутся из этих часов, а не из `now()` СУБД.
- **Альтернативы:** библиотеки подмены времени (freezegun, time-machine) — подменяют время глобально и плохо сочетаются с async и драйвером БД; `now()` PostgreSQL — нельзя управлять из теста.
- **Почему:** явная зависимость от часов делает сроки проверяемыми без ожидания реального времени.
- **Ограничение:** время процесса backend и время контейнера БД берутся с одних хост-часов Docker, расхождение не ожидается; в многосерверной установке нужна синхронизация (NTP).

## D-027. Docker Compose и запуск backend — реализовано (этап 1)

- **Выбрано:** `compose.yaml` с сервисами `db` (`postgres:17-alpine`, проверка готовности `pg_isready`) и `backend`; тесты — сервис `tests` в профиле `test` (тот же Dockerfile, стадия `test`). Backend при старте применяет миграции и создаёт демо-аккаунты (идемпотентно), затем запускает uvicorn. Порт PostgreSQL наружу не публикуется (не конфликтует с локальной СУБД; доступ — `docker compose exec db psql`). Все переменные имеют значения по умолчанию, поэтому `.env` не обязателен; `.env.example` описывает их.
- **Альтернативы:** монтирование исходников в контейнер с автоперезагрузкой (удобно для разработки, но поведение томов различается между ОС); отдельный контейнер для миграций.
- **Почему:** одна команда запуска одинаково работает в Windows, Linux и macOS.

# Этап 2 — конкурсы и идеи

Новых библиотек этап не добавляет.

## D-028. Снимок конкурса — один REST-запрос — реализовано (этап 2)

- **Выбрано:** `GET /api/contests/{id}` возвращает всё, что текущий пользователь может видеть в конкурсе прямо сейчас: данные конкурса, фазу, `revision`, `server_time`, видимые идеи и (только организатору) статистику. Фильтрация по роли и фазе выполняется на сервере, в SQL-запросе: во время подачи чужие идеи участника даже не читаются из БД. Снимок читается в транзакции `REPEATABLE READ` — все запросы снимка видят одно и то же состояние БД, поэтому `revision` точно соответствует данным.
- **Альтернативы:** отдельные запросы для конкурса, идей, статистики (клиенту пришлось бы склеивать данные разных моментов); фильтрация полей на клиенте (недопустимо — данные утекают в сеть).
- **Почему:** один снимок — одна точка проверки прав; его же клиент перечитывает по сигналу WebSocket (D-014).

## D-029. Шаблон изменяющего запроса: блокировка строки конкурса — реализовано (этап 2)

- **Выбрано:** любое изменение внутри конкурса (подача, правка, удаление идеи; на этапе 3 — голос и отзыв) выполняется в одной транзакции:
  1. `SELECT … FROM contests WHERE id = … FOR UPDATE` — блокировка строки конкурса;
  2. «сейчас» берётся из часов **после** получения блокировки;
  3. проверки: права, фаза, версия;
  4. изменение данных и `revision = revision + 1`;
  5. `COMMIT` снимает блокировку.
- **Что это даёт:** изменения одного конкурса выполняются строго по очереди; запрос, который ждал блокировку и дождался её уже после срока, будет отклонён — момент принятия решения не раньше момента проверки. Разные конкурсы друг друга не блокируют.
- **Альтернативы:** SERIALIZABLE с повторами (сложнее объяснить и тестировать); только ограничения БД без блокировки (не защищает связку «проверка фазы + запись» и порядок `revision`).
- **Цена:** запросы одного конкурса не выполняются параллельно; для внутреннего конкурса с десятками участников это незаметно.

## D-030. Коды ошибок доступа — реализовано (этап 2)

| Ситуация | Код |
|---|---|
| нет входа или токен недействителен | 401 |
| конкурс существует, но пользователь не в списке участников (и не организатор) | 404 — существование конкурса не раскрывается |
| чужая идея (правка/удаление) или несуществующая идея | 404 — существование чужой идеи не раскрывается |
| голос или отзыв: несуществующая идея, идея в невидимом конкурсе, чужая идея во время подачи | 404 «Идея не найдена» — один и тот же ответ (D-038) |
| действие запрещено ролью в видимом конкурсе (организатор подаёт идею; сотрудник создаёт конкурс) | 403 |
| действие запрещено фазой (подача после срока, удаление после финала) | 409 |
| правка устаревшей версии идеи | 409 + актуальные данные идеи |
| ошибка в данных запроса | 422 |

## D-031. Идемпотентность создания и правки — реализовано (этап 2)

- **Выбрано:** конкурс и идея создаются с `client_request_id` (UUID, его создаёт форма при открытии). Ограничения `UNIQUE(created_by, client_request_id)` и `UNIQUE(author_id, client_request_id)`. Повтор запроса возвращает уже созданный объект с кодом 200 (первый — 201), `revision` не меняется. Повтор подачи **после** срока тоже возвращает существующую идею: это повтор уже принятого действия, а не новая подача.
- Правка передаёт `version`. Если версия устарела, но текст совпадает с текущим (повтор той же правки, например двойное нажатие), возвращается 200 без изменений; если текст другой — 409 с актуальной идеей.
- Расширяет D-006.

## D-032. Ограничения данных — реализовано (этап 2)

- Тема конкурса и название идеи — 1…200 символов, описание идеи — 1…5000 символов; пробелы по краям обрезаются, строка из одних пробелов отклоняется.
- Сроки принимаются только с часовым поясом (ISO 8601 с `Z` или смещением); без пояса — 422, чтобы время не толковалось по-разному на клиенте и сервере.
- Список участников — только сотрудники (не организатор), хотя бы один. Если список не передан — все сотрудники.

# Этап 3 — голоса, результаты, конкурентность

Новых библиотек этап не добавляет.

## D-033. Таблица голосов — реализовано (этап 3)

- **Выбрано:** `votes (idea_id, voter_id, contest_id, created_at)`:
  - первичный ключ `(idea_id, voter_id)` — **один голос участника за одну идею обеспечивает сама БД**; за разные идеи голосовать можно (F5);
  - `idea_id → ideas.id ON DELETE CASCADE` — голоса удаляются той же командой `DELETE`, что и идея, в той же транзакции (F19);
  - `contest_id` дублируется из идеи, чтобы считать разных проголосовавших конкурса одним запросом по индексу `(contest_id, voter_id)`.
- **Альтернативы:** `UNIQUE(contest_id, voter_id)` — «один голос на конкурс», противоречит уточнению пользователя; проверка «уже голосовал» только в коде — при параллельных запросах обе проверки могут пройти до вставки; мягкое удаление голосов (`revoked_at`) — усложняет все подсчёты, а история отзывов заданием не требуется.
- Запрет голоса за свою идею проверяется сервером (автор известен из `ideas.author_id`); в схеме БД это не выражается без триггера — сознательно не используем.

## D-034. API голосования и повторы — реализовано (этап 3)

- `POST /api/ideas/{id}/vote` — отдать голос: 201, если голос создан; 200, если он уже был (повторное нажатие, вторая вкладка). Вставка `INSERT … ON CONFLICT DO NOTHING`.
- `DELETE /api/ideas/{id}/vote` — отозвать: 204 и когда голос был, и когда его уже нет (повторный отзыв ничего не меняет).
- Оба действия — по шаблону D-029: блокировка строки конкурса, «сейчас» после блокировки, проверки, `revision + 1` **только если что-то изменилось**.
- Ошибки: организатор — 403; своя идея — 403; не участник — 404; идея не найдена или уже удалена — 404; не фаза голосования (до или после) — 409.
- **Одновременные голос и удаление той же идеи** выстраиваются в очередь блокировкой конкурса: либо голос записан и затем удалён каскадом вместе с идеей, либо удаление прошло первым и голосующий получает 404. Голос без идеи невозможен ещё и потому, что внешний ключ не даст его вставить.

## D-035. Результаты и победитель — реализовано (этап 3)

- Результаты вычисляются при каждом запросе снимка (`COUNT` по `votes`), а не хранятся: после финала ни голоса, ни идеи измениться не могут (D-007, D-011), поэтому результат стабилен. Фиксация победителя в БД для писем — этап 5.
- Порядок результатов и победитель: больше голосов → раньше `submitted_at` → меньший `id` (D-008); функция `ranking_key` в `app/domain.py`. Победитель — первая идея в этом порядке; при нуле голосов — самая ранняя идея; без идей — победителя нет.
- **Видимость** (F15, F16):

  | | подача | голосование | финал |
  |---|---|---|---|
  | счёт голосов, порядок по результатам | — | только организатор | все |
  | победитель | — | — | все |
  | статистика (участники, идеи, проголосовавшие, голоса) | организатор | организатор | организатор |
  | «я голосовал за эту идею» (`voted_by_me`) | — | участник, только про свои голоса | участник |

- Во время голосования участникам идеи показываются в порядке подачи — порядок не выдаёт текущих лидеров.

## D-036. Анонимность голосования — реализовано (этап 3)

- **Выбрано:** API никогда не сообщает, кто за что голосовал — ни участникам, ни организатору, ни после финала. Участник видит только собственные голоса (`voted_by_me`), остальным доступны лишь суммы.
- **Почему:** уточнение пользователя «анонимное голосование»; в БД связь «голосующий — идея» хранится, потому что без неё нельзя обеспечить «один голос на идею» и отзыв.
- **Ограничение:** администратор с доступом к БД видит таблицу `votes`; анонимность обеспечивается на уровне приложения.

## D-037. Число проголосовавших — реализовано (этап 3)

- `COUNT(DISTINCT voter_id)` по действующим голосам конкурса (D-010): участник, отдавший три голоса, считается один раз; отозвавший все голоса или чьи голоса исчезли вместе с удалённой идеей — не считается.

# Исправления по проверке качества (REVIEW.md, группа 1)

## D-038. Проверка ввода и единые ответы «не найдено» — реализовано (2026-11-03)

- **Недопустимые символы.** Строки, которые попадают в БД (логин, тема конкурса, название и описание идеи), отклоняются с 422, если содержат символ NUL (код 0): PostgreSQL не может его сохранить, и раньше запрос падал с 500 (REVIEW A1). Общий валидатор — `app/schemas.py`.
- **Ответ 422 без присланного значения.** Одиночный суррогат Юникода (REVIEW A2) Pydantic отклоняет сама, но стандартный ответ FastAPI повторяет присланное значение в поле `input`, а такой символ не кодируется в UTF-8 — сервер падал с 500 при записи ответа. Свой обработчик 422 (`app/main.py`) возвращает тот же формат без поля `input`; заодно в ответ не попадает, например, присланный пароль.
- **Границы номеров.** Номера конкурсов и идей в адресе — `1 … 2147483647` (столбцы `INTEGER`); вне границ — 422 вместо 500 (REVIEW A3). Общий тип `IdPath`.
- **Голосование не раскрывает чужие идеи.** Голос и отзыв отвечают одинаково — 404 «Идея не найдена» — для несуществующей идеи, идеи в конкурсе, где пользователь не участник, и чужой идеи во время подачи (REVIEW Б1). Своя идея во время подачи по-прежнему даёт 409 «Голосование ещё не началось»: её участник видит.
- **Вход не держит соединение БД во время проверки пароля.** После чтения пользователя короткая транзакция завершается, scrypt выполняется без соединения (REVIEW В1).
- **Альтернативы:** для символов — молча удалять их (меняет текст пользователя без его ведома); для номеров — отвечать 404 (нужна отдельная обработка, а 422 честно говорит «неверный номер»); для голосования — оставить разные ответы (утечка числа чужих идей).
- Новых библиотек нет.

# Этап 4 — реальное время

## D-039. Протокол WebSocket — реализовано (этап 4)

Развивает D-014 (сигналы вместо данных) и D-003 (токен первым сообщением).

- **Адрес:** `ws://<сервер>/api/ws`, одно соединение на вкладку.
- **Вход:** первым сообщением клиент присылает `{"type": "auth", "token": "…"}`, иначе соединение закрывается:
  - нет сообщения за `WS_AUTH_TIMEOUT_SECONDS` (по умолчанию 5 с) — код закрытия `4408`;
  - сообщение не того вида — `4400`;
  - токен недействителен или сессия истекла — `4401`.
  
  При успехе сервер отвечает `{"type": "ready", "user_id": …, "server_time": …}`. Токен не передаётся в адресе: адреса попадают в журналы серверов.
- **События** — сигналы без данных конкурса:
  - `{"type": "contest_changed", "contest_id": N, "revision": R}` — изменение в конкурсе зафиксировано в БД;
  - `{"type": "phase_changed", "contest_id": N, "revision": R}` — наступил срок раунда (D-040);
  - `{"type": "contests_changed"}` — создан конкурс, в котором пользователь участвует (или любой — для организатора).
  
  Получив сигнал, клиент перечитывает снимок через REST, где проверяются права.
- **Кому отправляется.** Только тем, чей экран от изменения меняется. Так меньше лишних запросов, и по сигналам нельзя следить за чужой активностью (REVIEW Б2):

  | Изменение | Организаторы | Автор действия (все его вкладки) | Остальные участники |
  |---|---|---|---|
  | подача, правка, удаление идеи во время подачи | да | да | нет — чужие идеи им не видны |
  | удаление идеи во время голосования | да | да | да — идея исчезает у всех |
  | голос, отзыв голоса | да | да (`voted_by_me` в других вкладках) | нет — счёт им не виден |
  | наступление срока | да | — | да |
  | создание конкурса | да | — | участники нового конкурса |

  Не участникам конкурса сигналы о нём не отправляются никогда.
- **Публикация — только после успешного `COMMIT`.** Отклонённые и повторные запросы, которые ничего не изменили, сигналов не дают.
- **Очередь на каждое соединение.** Отправка сигнала только кладёт его в очередь соединения, поэтому медленный клиент не задерживает ответ HTTP. Если очередь переполнена (клиент не читает), соединение закрывается кодом `1013`. Клиент переподключится и перечитает снимок.
- **Выход и срок сессии.** Выход закрывает соединения этой сессии (код `4401`), другие вкладки остаются. Соединение истёкшей сессии закрывается при следующей отправке ему сигнала.
- **Поддержание связи:** клиент может прислать `{"type": "ping"}`, сервер отвечает `{"type": "pong"}`. Остальные сообщения игнорируются.
- **Порядок.** Сигналы разных изменений могут прийти не по порядку `revision`, потому что публикуются после коммита, вне блокировки. Это безопасно: сигнал только просит перечитать снимок, а снимок всегда актуален. Клиент отбрасывает ответы старее уже применённого (D-040).
- **Альтернативы:**
  - подписка клиента на конкретный конкурс (лишний шаг протокола; получателей сервер и так знает по списку участников);
  - отправка сигнала всем участникам при любом изменении (лишние запросы и утечка активности);
  - отправка прямо из обработчика без очереди (медленный клиент задерживал бы ответ).
- **Ограничение:** один процесс backend (D-014).

## D-040. Сигнал в момент срока и защита от устаревших снимков — реализовано (этап 4)

- **Проблема (REVIEW В3).** Фаза вычисляется по часам, поэтому в момент срока в БД ничего не меняется и `revision` прежний. Без отдельного сигнала экраны не узнают, что раунд закрылся.
- **Выбрано:** фоновая задача в процессе backend. Она спит до ближайшего срока (не дольше `DEADLINE_MAX_SLEEP_SECONDS`, по умолчанию 30 с), просыпается раньше при создании конкурса, а затем рассылает `phase_changed` по конкурсам, чей срок наступил с прошлой проверки. Каждый срок объявляется один раз.
- **Клиент (этап 6)** держит ещё и собственный таймер до ближайшего срока с поправкой на `server_time`: если сигнал потеряется, экран всё равно переключится.
- **Устаревший снимок** клиент определяет по паре (`revision`, `server_time`): у двух снимков до и после срока `revision` одинаковый, различает их только время сервера.
- **Альтернативы:**
  - только таймер на клиенте (при расхождении часов или «уснувшей» вкладке экран не переключится);
  - опрос сервера раз в несколько секунд (лишняя нагрузка, задержка);
  - сигнал из обработчика заданий этапа 5 (он проверяет задания раз в несколько секунд, а для сроков подачи заданий нет).

## D-041. Тесты WebSocket: настоящий сервер и клиент `websockets` — реализовано (этап 4)

- **Выбрано:** в тесте запускается настоящий uvicorn на свободном порту внутри того же цикла событий, клиент — библиотека `websockets==17.3`. Она уже входит в `uvicorn[standard]`, а в `requirements-dev.txt` закреплена явно, потому что тесты используют её напрямую. HTTP-запросы идут через тот же объект приложения, поэтому управляемые часы и БД общие.
- **Как проверяется отсутствие сигнала:** после действия тест шлёт `ping`. Сигналы кладутся в очередь до ответа HTTP, поэтому если следующим сообщением пришёл `pong`, сигнала не было. Это надёжнее, чем ждать «тишину» заданное время.
- **Альтернативы:**
  - `TestClient` из Starlette — запускает приложение в отдельном цикле событий, а соединения asyncpg к циклу привязаны;
  - `httpx-ws` — ещё одна зависимость ради того же.

# Этап 5 — расписание и почта

Новых библиотек этап не добавляет. Реализует D-010, D-012, D-015, D-016.

## D-042. Таблица заданий и план заданий конкурса — реализовано (этап 5)

- **Таблица** `jobs`: конкурс, вид (`remind_submission`, `remind_voting`, `finalize`), момент запуска `run_at`, статус (`pending`, `done`, `skipped`, `failed`), число попыток, последняя ошибка, время завершения, пояснение (`note`). Ограничение `UNIQUE(contest_id, kind)`: у конкурса не бывает двух одинаковых заданий.
- **Задания создаются в той же транзакции, что и конкурс.** Конкурс не может остаться без расписания.
  - `remind_submission` — `submission_deadline − REMINDER_LEAD`;
  - `remind_voting` — `voting_deadline − REMINDER_LEAD`;
  - `finalize` — ровно `voting_deadline`.
- **Короткий раунд** (D-015). Если момент напоминания раньше начала раунда, задание сразу получает статус `skipped` с пояснением «раунд короче срока напоминания», и напоминание не отправляется. Начало раунда подачи — создание конкурса, начало голосования — срок подачи. Момент напоминания, равный началу раунда, допустим.
- **`REMINDER_LEAD` фиксируется при создании конкурса** в `run_at`. Его изменение действует на новые конкурсы.
- **Существующие конкурсы** (созданные до этапа 5) получают задания миграцией `0004` с `REMINDER_LEAD` по умолчанию (24 ч). Просроченные задания обработчик выполнит или пропустит по правилам D-043.
- **Альтернативы:**
  - создавать задания обработчиком по таблице конкурсов (расписание не было бы явным и проверяемым);
  - одно задание «следующий шаг конкурса» (сложнее объяснить статусы и повторы).

## D-043. Обработчик заданий — реализовано (этап 5)

- **Фоновая задача в процессе backend.** Она спит до ближайшего `run_at` (не дольше `JOBS_MAX_SLEEP_SECONDS`, по умолчанию 30 с) и просыпается раньше при создании конкурса.
- **Одно задание — одна транзакция:**
  1. `SELECT … FROM jobs WHERE status = 'pending' AND run_at <= now ORDER BY run_at, id LIMIT 1 FOR UPDATE SKIP LOCKED` — взять задание. Строку, которую уже обрабатывает другая копия обработчика, `SKIP LOCKED` пропустит.
  2. `SELECT … FROM contests … FOR UPDATE` — та же блокировка, что у изменяющих запросов (D-029). Задание дожидается всех начатых изменений, например голоса, принятого за миллисекунду до срока (REVIEW В2).
  3. «Сейчас» берётся после блокировок. Проверяется, актуален ли раунд, и **заново** вычисляются получатели.
  4. Письма и отметка «выполнено» записываются в одной транзакции. Письмо без отметки или отметка без писем невозможны, поэтому после перезапуска выполненное не повторяется, а невыполненное — выполняется.
- **Простой сервера** (D-015). После запуска выполняются все просроченные задания:
  - напоминание отправляется, только если его раунд ещё открыт; иначе `skipped` «раунд уже закрыт»;
  - финал выполняется с опозданием. Результаты при этом видны с момента срока (фаза вычисляется по часам), а письма придут позже.
- **Ошибка при выполнении** откатывает работу задания (точка сохранения), но не освобождает его:
  - `attempts + 1`, текст ошибки сохраняется, повтор — через 5 с × номер попытки;
  - после 5 неудачных попыток — `failed`; задание видно в БД.
- **Порядок блокировок:** задание, затем конкурс. Изменяющие запросы блокируют только конкурс и заданий не ждут, поэтому взаимной блокировки нет.
- **Несколько копий обработчика** безопасны (`SKIP LOCKED` и ограничения `UNIQUE`), но основной сценарий — один процесс (D-015).
- **Альтернативы:**
  - APScheduler с хранилищем в БД (вторая система расписания рядом с таблицей, хуже видна);
  - Celery и Redis (лишние компоненты для одного процесса);
  - обработка всех заданий одной транзакцией (одна ошибка останавливала бы остальные).

## D-044. Получатели писем — реализовано (этап 5)

Проверяются в момент выполнения задания, по текущему состоянию (D-010).

| Письмо | Получает | Не получает |
|---|---|---|
| напоминание о подаче | участник конкурса без единой неудалённой идеи в нём | подавший идею; организатор; сотрудник вне списка участников |
| напоминание о голосовании | участник без единого действующего голоса, **если есть хотя бы одна чужая идея**, за которую он может проголосовать | проголосовавший; участник, чьи идеи — единственные в конкурсе (голосовать ему не за что); организатор; не участник |
| итоговое | каждый участник из списка — ровно одно письмо; автору победившей идеи — вариант «ваша идея победила» | организатор и не участники |

- **Голосовать не за что.** Если идей в конкурсе нет, напоминание о голосовании не отправляется никому: `skipped` «идей нет — голосовать не за что».
- **Итоговое письмо** содержит результаты по правилу победителя (D-008): названия, число голосов, авторов (после финала они открыты) и правило ничьей. Если идей нет — «конкурс завершён, идей не подано».
- **Дубли** исключает `UNIQUE(contest_id, recipient_id, kind)` в таблице писем. Победитель получает **одно** письмо вида `final` (D-012).
- Время в письмах — UTC с пометкой «UTC»: часовой пояс получателя серверу неизвестен.

## D-045. Почтовая заглушка: таблица писем, API, сигнал — реализовано (этап 5)

- **Таблица** `emails`: получатель, адрес на момент отправки, конкурс, вид (`reminder_submission`, `reminder_voting`, `final`), тема, текст, время создания.
- **`GET /api/emails`** — участник видит только свои письма, организатор — журнал всех (D-016). Необязательный фильтр `contest_id`. Порядок — новые сверху.
- **Сигнал WebSocket** `{"type": "mail_changed"}` после записи писем — получателям и организаторам (D-039), чтобы страница почты обновилась без перезагрузки.
- **Ограничение:** письмо — запись в БД. Реальная доставка, адреса и спам-фильтры не проверяются.

## D-046. Переменная `REMINDER_LEAD` — реализовано (этап 5)

- **Формат** — длительность `ЧЧ:ММ:СС` (например, `24:00:00`, `00:02:00`) или ISO 8601 (`PT2M`). По умолчанию `24:00:00`, как в задании. Ноль и отрицательные значения при запуске отклоняются.
- **Меньшее значение — только для демонстрации:** так видно работу напоминаний без ожидания суток. README говорит об этом прямо.
