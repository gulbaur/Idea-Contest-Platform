## Как читать этот документ

У каждого предложения есть номер (например, **С-3**) — по нему удобно выбирать. Внутри четыре пункта:

- **Что** — что именно меняем или добавляем.
- **Зачем** — какую проблему это решает.
- **Как для пользователя** — что человек увидит и сделает.
- **Технически** — что меняется в коде, объём работы и риски.

**Приоритет:**

| Метка | Значение |
|---|---|
| 🔴 **Обязательно** | Либо это уже дефект, либо без этого выбранная вами функция будет небезопасной или сломает правила задания |
| 🟡 **Рекомендую** | Заметно улучшает сервис при разумной цене |
| ⚪ **По желанию** | Полезно, но можно жить и без этого |

**Объём:** **S** — небольшая правка; **M** — заметная доработка с миграцией БД или новой страницей; **L** — большая работа, затрагивающая многие файлы. Объём оценён относительно, а не в днях: точные сроки появятся в плане этапов.

**Общее условие для всего, что ниже.** Правила задания остаются в силе:

- организатор не видит авторов до финала и не голосует;
- голосовать можно только за чужие идеи, один голос на идею;
- время и права проверяет сервер.

Сценарий проверяющего тоже должен работать как сейчас: одна команда запуска, демо-аккаунты, две вкладки под разными пользователями. Каждое изменение проверяется тестами, плюс все 232 + 72 + 21 существующих.

## Как устроено сейчас (коротко)

Факты из кода, на которых построены предложения:

- **Вход.**
  - Логин и пароль; пароли хранятся как хеш scrypt, а не в открытом виде.
  - Сервер выдаёт случайный токен и хранит только его хеш. Токен лежит в `sessionStorage` вкладки, поэтому у каждой вкладки свой вход.
  - Регистрации нет. Аккаунты создаёт сид-скрипт: шесть демо-пользователей с общим публичным паролем.
  - Ограничения попыток входа нет. Сменить пароль нельзя, отключить пользователя нельзя.
  - Демо-пароль записан прямо в код страницы входа (`LoginPage.vue`), поэтому он показывается всегда.
- **Роли.** Две глобальные роли: `organizer` и `employee`. Любой организатор видит все конкурсы. Проверки `role != ORGANIZER` разбросаны по нескольким файлам.
- **Конкурс.**
  - Есть только тема (до 200 символов), два срока и список участников.
  - После создания ничего не меняется: ни сроки, ни участники. Отменить конкурс нельзя.
- **Список конкурсов.**
  - Сервер отдаёт все конкурсы сразу, без постраничной загрузки.
  - Интерфейс показывает карточки в несколько колонок и фильтр по фазе.
  - Участник по списку не видит, нужно ли ему что-то сделать.
- **Почта.**
  - Три вида писем (напоминание о подаче, напоминание о голосовании, итоги), и все только участникам.
  - Организатор не получает своих писем: он видит журнал чужих.
  - Сервер отдаёт не больше **200** писем, и интерфейс не умеет загрузить остальные.
  - Отметки «прочитано» нет. Время в письмах в UTC.
- **Реальное время.**
  - Сигналы через WebSocket рассылает один процесс backend.
  - Список участников конкурса кешируется в памяти: это безопасно, пока он не меняется.
- **Фоновые задачи.** Расписание хранится в таблице `jobs`. Если задание не выполнено пять раз подряд, его видно только на экране конкурса.
- **Интерфейс.**
  - Свои стили на CSS-переменных, без UI-библиотеки.
  - Тема переключается только по настройке системы, переключателя нет. Шрифт системный.
  - Все тексты на русском прямо в коде компонентов. Сервер тоже присылает тексты ошибок на русском.

## 1. Список конкурсов

### К-1. Вертикальный список вместо карточек — 🟡, объём M

**Что.** Каждый конкурс занимает одну строку на всю ширину. Колонки выровнены, поэтому взгляд скользит сверху вниз и сравнивает конкурсы между собой.

**Варианты формата:**

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Таблица** | Самая плотная; сортировка по клику на заголовок колонки | На телефоне таблица неудобна: нужна прокрутка вбок или отдельная вёрстка |
| **Строки списка с колонками** (рекомендую) | На компьютере выглядит как таблица, на телефоне каждая строка складывается в компактный блок; можно добавить вторую строку подписи | Сортировка не кликом по колонке, а отдельным выпадающим списком |
| Карточки (сейчас) | Красиво при 3–5 конкурсах | При 30+ конкурсах трудно искать и сравнивать сроки |

**Как для пользователя (компьютер):**

```
┌─────────────────────────────────────────────────────────────────────────────────────────┐
│ Конкурсы                                        [🔍 Поиск по теме ]  [+ Новый конкурс] │
│ [Все 12] [Приём идей 3] [Голосование 2] [Завершены 7]        Сортировка: ближайший срок │
├─────────────────────────────────────────────────────────────────────────────────────────┤
│ КОНКУРС                          ЭТАП             СЛЕДУЮЩИЙ СРОК          УЧАСТИЕ        │
│▌Как сократить время на совещания ● Голосование    до 8 нояб., 18:00       Голосов 5 из 12│
│ создан 3 нояб. · 12 участников   ▓▓▓▓▓▓▓▓░░░      осталось 2 д 4 ч        идей 8         │
│▌Как сделать офис уютнее          ● Приём идей     до 10 нояб., 12:00      идей 3         │
│ создан 4 нояб. · 5 участников    ▓▓▓░░░░░░░░      осталось 4 д 1 ч                       │
│▌Обеды в офисе                    ✓ Завершён       итоги 1 нояб.           🏆 «Чат-бот…»  │
└─────────────────────────────────────────────────────────────────────────────────────────┘
```

- Цветная полоска `▌` слева показывает фазу.
- Мини-шкала времени показывает, какая часть всего конкурса прошла.
- Строка целиком — ссылка на конкурс.
- Колонка «Участие» зависит от роли (см. К-2).

**Телефон** — та же строка в три коротких ряда: тема → значок фазы и срок → участие.

**Технически.**

- Интерфейс: новый компонент строки вместо `ContestCard.vue`; переделать `ContestsPage.vue`.
- Сервер: чтобы показать «идей 8, голосов 5 из 12», в ответ `GET /api/contests` нужно добавить счётчики. Их надо считать одним запросом к БД для всех конкурсов сразу, а не отдельным запросом на каждый конкурс: иначе 100 конкурсов дадут 100 запросов.
- **Риск — анонимность.** Счётчики должны подчиняться тем же правилам, что и экран конкурса. Участник во время подачи не видит, сколько идей подали другие (сейчас не видит и на странице конкурса). Нужны тесты на это.
- Браузерные E2E ищут элементы карточек — их придётся обновить.

### К-2. Группа «Ждут вашего действия» и отметки участия — 🟡, объём M

**Что.** Сверху списка — то, что требует внимания именно этого человека.

**Как для пользователя.**

- **Участник** видит сверху группу «Ждут вашего действия»:
  - идёт приём идей, а вы ещё не подали идею;
  - идёт голосование, вы ещё не голосовали и есть чужие идеи.

  Ниже — «Идут» и «Завершены». Завершённые свёрнуты: видны последние пять и кнопка «Показать все». В колонке «Участие» — «Вы подали 2 идеи», «Вы проголосовали ✓» или «Нужно проголосовать».
- **Организатор** видит идущие конкурсы, отсортированные по ближайшему сроку. В колонке «Участие» — счётчики. Сверху — предупреждения: «в конкурсе нет идей, а приём закрывается завтра».

**Зачем.** Сейчас участник узнаёт, что пора голосовать, только из напоминания за сутки до конца. Если конкурсов много, нужное легко пропустить.

**Технически.**

- В ответ списка добавляется блок «моё участие»: сколько моих идей, голосовал ли я, есть ли за кого голосовать. Это те же правила, по которым сервер уже решает, кому слать напоминание (D-010), поэтому логику можно переиспользовать.
- Список должен обновляться в реальном времени. Если организатор держит список открытым, а участники голосуют в десяти конкурсах, список не должен перезагружаться на каждый голос. Нужно объединять сигналы: не чаще раза в 1–2 секунды.

### К-3. Поиск, сортировка, постраничная загрузка — 🟡, объём M

**Что.**

- Поиск по теме.
- Сортировка: «ближайший срок», «сначала новые», «сначала старые».
- Сервер отдаёт список порциями, например по 25, а внизу кнопка «Показать ещё».

**Зачем.** Сейчас сервер отдаёт все конкурсы сразу. При сотнях конкурсов это медленно и неудобно.

**Технически.**

- Параметры `phase`, `q`, `sort`, `limit`, `cursor` у `GET /api/contests`.
- Фильтр по фазе считается в SQL по срокам: фаза в базе не хранится, и это правильно (D-007).
- Порции выдаются по курсору — метке «продолжить после этой строки», а не по номеру страницы. С номером страницы при появлении нового конкурса строки съезжали бы и повторялись.

## 2. Почта и уведомления

### П-1. Почта постранично — 🔴 дефект, объём S

**Что сейчас не так.** `GET /api/emails` по умолчанию отдаёт не больше 200 писем, а страница «Почта» не умеет загрузить остальные. Счёт простой: 50 сотрудников × 10 конкурсов × до 3 писем — это до 1500 писем. После двухсотого старые письма молча пропадают из вида: ни ошибки, ни подсказки.

**Как исправить.** Постраничная загрузка по курсору и кнопка «Показать ещё». Нужен тест: 250 писем — все доступны.

### П-2. «Входящие» для всех и отдельный «Журнал рассылки» — 🟡 ваша просьба, объём M

**Что.** Вместо одной страницы «Почта», которая для организатора работает как журнал, — два раздела с разными задачами:

| | **Входящие** | **Журнал рассылки** |
|---|---|---|
| Кто видит | Каждый, включая организатора | Только организатор или администратор (см. С-1) |
| Что внутри | Письма, адресованные **мне** | Все отправленные письма всех людей |
| Зачем | Узнать, что произошло и что делать | Ответить на вопрос «почему Анна говорит, что не получила напоминание?» |
| Вид | Как почтовый ящик: список, текст письма, непрочитанные | Таблица: время, конкурс, вид, получатель, тема; поиск по получателю, фильтры |

**Нужен ли журнал вообще? Мой ответ: да, но отдельно.**

- В настоящем сервисе журнал — инструмент поддержки: он показывает, что письмо ушло, когда и кому.
- В нашем проекте почта — заглушка, поэтому журнал ещё и единственный способ показать проверяющему, что рассылка работает.
- Смешивать журнал с личными уведомлениями не нужно: организатор тонет в чужих письмах. Вы правильно это заметили.

**Правило D-058 остаётся.** До финала напоминания в журнале скрыты: по их получателям видно, кто ещё не подал идею, а значит — кто автор поданных. Можно показывать их без имён: «Напоминание о подаче — 3 получателя».

**Варианты устройства:**

| Вариант | Как устроено | Плюсы | Минусы |
|---|---|---|---|
| **А. Одна таблица писем** (рекомендую) | Письма организатору хранятся в той же таблице `emails`. «Входящие» — письма, где получатель = я; журнал — все письма | Минимум изменений; одна логика рассылки; уже проверено тестами | Каждое уведомление — это «письмо» |
| Б. Отдельные таблицы «уведомления» и «письма» | Короткие уведомления в интерфейсе (колокольчик) отдельно от писем на почту, как в Jira или Slack | Гибко: уведомление можно показать без письма | Две параллельные системы, дублирование, больше тестов |

Рекомендую **А**: всё, что нужно сейчас, оно даёт, а переход к **Б** позже ничего не ломает.

### П-3. Личные уведомления организатора — 🟡 ваша просьба, объём M

**Что.** Организатор получает во «Входящие» письма о своих конкурсах. **Кому из организаторов:** рекомендую — создателю конкурса. Если организаторов несколько, остальным чужие конкурсы не шумят.

| Когда | Письмо организатору | Почему полезно |
|---|---|---|
| За сутки до конца приёма идей | «Пока подано 3 идеи от 2 из 12 участников. Напоминание отправлено 10 участникам» | Можно лично подтолкнуть коллег |
| Конец приёма идей | «Приём идей завершён: 8 идей. Голосование открыто до …» | Понятно, что конкурс перешёл в следующую фазу |
| Конец приёма идей, а идей нет | «Идей не подано — голосования не будет, конкурс завершится без победителя» | Предупреждение, на которое можно отреагировать (А-3 — отменить) |
| За сутки до конца голосования | «Проголосовали 5 из 12» | Видно, хватает ли активности |
| Финал | «Конкурс завершён. Победила идея «…» (автор …, 6 голосов)» и полная таблица | Главный результат |
| Сбой рассылки (А-8) | «Не удалось отправить итоговые письма. Повторных попыток больше не будет» | Сейчас сбой видно только на странице конкурса |

**Анонимность.** В письмах организатору до финала — только числа, без имён. Эти числа организатор уже видит на экране конкурса, так что новых сведений письма не дают. Нужен тест.

**Технически.**

- Новые виды писем, миграция ограничений таблиц `emails` и `jobs`.
- Новое задание расписания «приём идей закрыт» на момент первого срока.
- Демо-конкурсы (D-054) проигрывают историю заданий, поэтому новые письма появятся и в них.

### П-4. Новые письма участникам — 🟡, объём M

| Письмо | Когда | Зачем |
|---|---|---|
| «Вас пригласили в конкурс «…»» | При создании конкурса или добавлении участника (С-9) | **Сейчас участник узнаёт о конкурсе, только если сам зайдёт в сервис или получит напоминание за сутки до конца.** Для настоящего сервиса это главный пробел |
| «Голосование открыто» | В момент окончания приёма идей, если есть идеи | Сейчас о начале голосования никто не сообщает |

Существующие письма остаются: напоминания тем, кто ещё не участвовал, и итоги всем. Ограничение «одно письмо каждого вида на человека в конкурсе» сохраняется, так что дублей не будет.

### П-5. Непрочитанные и счётчик в меню — 🟡, объём S

- В меню — «Входящие **3**». Непрочитанные письма выделены, открытое письмо становится прочитанным, есть кнопка «Отметить все прочитанными».
- Технически: колонка `read_at` в таблице писем. Счётчик обновляется по уже существующему сигналу `mail_changed`.
- Заодно сигнал можно сузить: сейчас он уходит **всем** организаторам на каждое письмо любого конкурса.

### П-6. Время в письмах в часовом поясе получателя — 🟡, объём S

- Сейчас интерфейс показывает время в поясе браузера, а письма — в UTC («18:00 UTC»). Сотрудник в Алматы видит в письме одно время, на сайте другое.
- Предложение: часовой пояс хранится в настройках пользователя (Д-4). При первом входе он определяется браузером автоматически, письма пишутся в этом поясе.
- Пока пояс не известен, остаётся UTC с пометкой, как сейчас.

## 3. Дизайн и настройки

### Д-1. Сначала макет на согласование — 🟡, объём S

**Что.** До изменения кода я делаю статический макет ключевых экранов: список конкурсов, страница конкурса, входящие, настройки, сотрудники. Каждый экран — в светлой и тёмной теме, на компьютере и телефоне. Вы смотрите его в браузере и говорите, что нравится, а что нет.

**Зачем.** Вам не нравится текущий стиль, но словами «современно и аккуратно» каждый понимает своё. Согласовать вид на картинке дешевле, чем переделывать готовые страницы с тестами.

### Д-2. Дизайн-система — 🟡 ваша просьба, объём L

**Что не так сейчас:**

- градиенты и фиолетовые акценты выглядят «игриво», а не по-деловому;
- крупные скругления (18 px) и много цветных плашек;
- нет единой шкалы размеров текста и отступов: размеры подобраны по месту в каждом компоненте (0,78 rem, 0,85 rem, 0,88 rem, 0,92 rem…).

**Предлагаемые принципы:**

- **Спокойный нейтральный фон, один акцентный цвет.** Цвет — только там, где он что-то значит: фаза конкурса, успех, ошибка, предупреждение. Без декоративных градиентов.
- **Границы вместо теней.** Тонкие линии разделяют блоки; тень — только у всплывающих окон.
- **Плотность для работы.** Списки компактнее, чтобы на экране помещалось больше строк.

**Из чего состоит дизайн-система** — это набор правил в одном файле плюс набор готовых компонентов:

| Часть | Что входит |
|---|---|
| Цвета | Нейтральная шкала из 10 оттенков серого; акцент; смысловые цвета (успех, предупреждение, ошибка, информация); три цвета фаз; всё — в светлом и тёмном варианте |
| Типографика | Шкала размеров 12 / 13 / 14 / 16 / 18 / 22 / 28 px с подобранной высотой строки; основной текст 14 px — стандарт для рабочих сервисов; цифры одинаковой ширины в таблицах и таймерах |
| Отступы | Шаг 4 px: 4, 8, 12, 16, 24, 32, 48 — только эти значения |
| Скругления, тени, анимации | 2–3 значения каждого вида; анимации короткие (150 мс), отключаются, если в системе включено «уменьшить движение» |
| Точки перестройки | Телефон < 640 px, планшет < 1024 px, компьютер ≥ 1024 px |
| Компоненты | Кнопка, поле ввода, выпадающий список, флажок, переключатель, вкладки, значок, строка списка, панель, диалог, всплывающее сообщение, пустое состояние, заглушка загрузки, аватар, подсказка, «Показать ещё» |

**Доступность:**

- контраст текста не ниже нормы WCAG AA;
- видимая рамка фокуса;
- всё работает с клавиатуры;
- подписи для экранных дикторов.

**Свои компоненты или готовая библиотека:**

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Свои компоненты на CSS-переменных** (рекомендую) | Полный контроль над видом; маленький размер; уже так устроено (D-047); тесты остаются | Компоненты делаем сами — это часть объёма L |
| Библиотека (PrimeVue, Naive UI, Vuetify) | Готовые таблицы, диалоги, доступность | Свой узнаваемый вид, который всё равно придётся перекрашивать; больше размер; переписать почти все страницы и тесты |
| Tailwind CSS | Быстро верстать | Переписать все стили; классы в разметке тяжело читать новичку |

### Д-3. Боковое меню и адаптивная раскладка — 🟡 ваша просьба, объём M

**Почему боковое меню.** Сейчас в шапке два раздела. После изменений их станет до пяти: Конкурсы, Входящие, Журнал рассылки, Сотрудники, Настройки. В шапке они не поместятся, особенно на планшете. Боковое меню — стандарт рабочих сервисов (Jira, GitLab, Notion).

│    идей      │                                                       │
│              │  ┌ заголовок страницы ──────────── [главная кнопка] ┐ │
│ ▸ Конкурсы   │  │ фильтры / поиск                                   │ │
│ ▸ Входящие 3 │  ├───────────────────────────────────────────────────┤ │
│ ─ Управление │  │                                                   │ │
│ ▸ Журнал     │  │ содержимое (до 1200 px шириной)                   │ │
│ ▸ Сотрудники │  │                                                   │ │
│              │  └───────────────────────────────────────────────────┘ │

- **Компьютер** — меню с подписями. **Планшет** — узкая полоса значков с подсказками. **Телефон** — верхняя полоса с названием страницы и нижняя панель из 3–4 главных разделов. Остальные разделы — в «Ещё».

- Индикатор связи и «вошли как …» переезжают в низ меню.

### Д-4. Страница «Настройки» — 🟡 ваша просьба, объём M

**Что на странице:**

| Настройка | Варианты |
|---|---|
| Тема | Светлая / Тёмная / **Как в системе** (по умолчанию) |
| Язык | Русский / English (см. Д-5) |
| Шрифт | 3–4 варианта с поддержкой кириллицы и живым образцом текста. Предлагаю: **Системный** (быстрее всего), **Inter** (нейтральный современный), **IBM Plex Sans** (строгий корпоративный), **Golos Text** (создан для русскоязычных интерфейсов) |
| Часовой пояс | Определяется автоматически, можно выбрать вручную (для П-6) |
| Профиль | Имя и логин (только просмотр), смена пароля (С-5) |

**Где хранить настройки — важный момент из-за входа «каждая вкладка отдельно» (D-003):**

| Вариант | Плюсы | Минусы |
|---|---|---|
| Только в браузере (`localStorage`) | Просто, без изменений сервера | Хранилище общее для всех вкладок браузера. Анна в одной вкладке выберет тёмную тему — и у Бориса в соседней вкладке тоже станет тёмная. На другом компьютере настроек нет |
| **На сервере у пользователя + копия в браузере** (рекомендую) | Настройки следуют за человеком: свои в каждой вкладке, на любом устройстве. Копия в браузере применяется до загрузки страницы, поэтому нет вспышки светлой темы | Нужны миграция, API и тесты |

**Технически.**

- В таблице `users` — колонки `theme`, `locale`, `font`, `timezone` с проверкой допустимых значений в БД. Они приходят вместе с ответом на вход и меняются запросом `PATCH /api/me/preferences`.
- Тема переключается атрибутом на странице, а не только настройкой системы. Небольшой скрипт в `index.html` применяет сохранённую тему ещё до запуска Vue.
- **Шрифты подключаются из самого проекта, а не с Google Fonts.** Во внутренней сети компании внешних запросов может не быть, и это ещё и вопрос приватности. Источник — пакеты `@fontsource/*`; это новая зависимость, её надо записать в DECISIONS.
- Загружается только выбранный шрифт, только форматы woff2 и наборы символов «латиница + кириллица»: около 30–60 КБ на начертание.

### Д-5. Английский язык интерфейса — 🟡 ваша просьба, объём L

**Это самый большой пункт.** Тексты сейчас есть не только в интерфейсе.

| Где тексты | Что делать |
|---|---|
| Около 20 компонентов интерфейса | Вынести все строки в словари `ru` и `en`. Использовать библиотеку **vue-i18n** — стандарт для Vue. Она умеет русские формы множественного числа («1 голос / 2 голоса / 5 голосов») и даты по языку. Свой самодельный словарь пришлось бы учить всему этому самим |
| Ошибки сервера («Срок окончания приёма идей должен быть в будущем») | Сервер присылает русский текст. Нужно, чтобы каждая ошибка имела машинный **код** (как уже есть у `request_id_reused`), а интерфейс показывал перевод по коду. См. А-5 |
| Письма | Пишутся на языке получателя по его настройке. Уже отправленное письмо не переводится — как в настоящей почте |
| Даты и числа | Формат по выбранному языку (сейчас везде `ru-RU`) |
| Темы конкурсов и тексты идей | Не переводятся: это то, что написали люди |

**Риски.**

- Пропущенные строки дадут экраны «наполовину на русском».
- Тесты ищут элементы по русскому тексту: в E2E около 80 таких мест. Тесты остаются на русском, а для английского добавляются проверка «в словарях `ru` и `en` одинаковый набор ключей» и короткий E2E на английском.

**Совет по порядку.** Подключить vue-i18n сразу при переделке дизайна (Д-2), чтобы новые страницы сразу писались через словарь. Английский словарь заполнить последним, когда все тексты устоятся. Иначе придётся переводить экраны, которые потом переделаются.

### С-1. Роли — 🟡 ваша просьба, объём M

**Варианты:**

| **Б. Три роли** (рекомендую) | **Сотрудник** участвует в конкурсах. **Организатор** создаёт и ведёт конкурсы. **Администратор** управляет сотрудниками и ролями, видит журнал рассылки и журнал действий | Разделение обязанностей — стандарт корпоративных систем. Кто ведёт конкурсы, не создаёт учётных записей, и наоборот | Больше проверок прав (см. А-4); новый демо-аккаунт `admin` |

- Несколько организаторов могут работать одновременно. В списке конкурсов есть фильтр «Мои / Все».
- **Защита от подделки голосов** держится на трёх вещах:
  - разделение ролей;
  - журнал действий (С-7);
  - ссылка-приглашение уходит на почту сотрудника, и администратор её не видит (С-3).

### С-2. Раздел «Сотрудники» — 🟡 ваша просьба, объём L

**Как для администратора.**

```
Сотрудники                                              [+ Пригласить сотрудника]
[🔍 Имя, логин или почта]  Отдел: [Все ▾]  Роль: [Все ▾]  Статус: [Активные ▾]

ИМЯ              ЛОГИН   ОТДЕЛ        РОЛЬ         СТАТУС        ПОСЛЕДНИЙ ВХОД
Анна Смирнова    anna    Маркетинг    Сотрудник    ● Активен     сегодня, 09:12   [⋯]
Глеб Лебедев     gleb    Разработка   Сотрудник    ◐ Приглашён   —                [⋯]
Ирина Павлова    irina   Продажи      Организатор  ● Активен     вчера            [⋯]
Пётр Сидоров     petr    Продажи      Сотрудник    ○ Отключён    12 окт.          [⋯]
```

- Меню `[⋯]`: «Изменить», «Сменить роль», «Отправить приглашение повторно» или «Сбросить пароль», «Отключить» или «Включить».
- **Пригласить** — форма: имя, логин, рабочая почта, отдел, роль. Сотрудник получает письмо со ссылкой.
- **Статусы:**
  - **Приглашён** — ссылка отправлена, пароль ещё не задан;
  - **Активен** — может входить;
  - **Отключён** — доступ закрыт, история сохранена.
- Сотрудников не удаляем совсем, только отключаем. Их идеи, голоса и письма — часть истории конкурсов: удаление сломало бы результаты прошлых конкурсов.
- ⚪ Импорт списка сотрудников из CSV-файла — полезно, когда людей сотни.

**Технически.**

- Миграция таблицы `users`: статус, отдел, время последнего входа, уникальная почта.
- Новые API `/api/admin/users…`, страница, тесты прав.
- Если два администратора одновременно меняют одного сотрудника, строка блокируется: так же, как сейчас конкурс (D-029).

### С-3. Первый вход по ссылке-приглашению — 🟡 ваша просьба, объём M

**Как для сотрудника.**

1. Приходит письмо: «Вас пригласили в «Конкурс идей». Чтобы задать пароль, откройте ссылку. Ссылка действует 72 часа».
2. По ссылке открывается страница: имя и логин уже заполнены, нужно дважды ввести пароль.
3. После этого — сразу вход.

**Правила безопасности:**

- ссылка одноразовая, действует ограниченное время, а повторная отправка отменяет прежнюю;
- в базе хранится только хеш токена ссылки, как у сессий сейчас: утечка базы не даёт рабочих ссылок;
- в журнале рассылки видно, что приглашение ушло, но **не видно самой ссылки**;
- «Сбросить пароль» работает так же: новая ссылка на почту, а все текущие сессии сотрудника закрываются.

**Как это показать в демонстрации.** Почта у нас заглушка: письмо со ссылкой никуда не уходит, а войти и прочитать его новый сотрудник не может. Решение — **демо-режим**: в нём администратор после приглашения видит ссылку на экране с пометкой «в рабочем режиме ссылка уходит только на почту сотрудника». В рабочем режиме ссылку не видит никто, кроме получателя.

### С-4. Отключение доступа — 🟡 ваша просьба, объём M

**Что происходит при отключении:**

- войти больше нельзя;
- **все открытые сессии удаляются, вкладки сотрудника сразу выходят** — WebSocket закрывается так же, как сейчас при выходе;
- в новые конкурсы сотрудника выбрать нельзя;
- в идущих конкурсах уже поданные идеи и голоса остаются: в момент подачи они были законными;
- отключённый сотрудник перестаёт получать напоминания и письма;
- включить обратно можно.

**Технически.**

- Проверка статуса при каждом запросе: она уже встроена в поиск сессии, нужно лишь добавить условие.
- Получатели писем фильтруются по статусу.
- **Риск.** В памяти сервера кешируется список участников конкурса, и сейчас это безопасно, потому что список не меняется (D-009). Как только участники или статусы начинают меняться (С-4, С-9), кеш нужно сбрасывать. Иначе отключённому человеку продолжат приходить сигналы — без данных, но всё же.

### С-5. Защита входа — 🔴 при настоящих учётных записях, объём M

Сейчас все пароли демонстрационные, и защиты от перебора нет. Когда люди задают свои пароли, она обязательна.

| Мера | Как |
|---|---|
| Ограничение попыток | После 5 неудачных попыток для пары «логин + адрес» вход на 15 минут отвечает «слишком много попыток». Счётчик хранится в PostgreSQL, Redis не нужен |
| Правила пароля | Не короче 10 символов, не совпадает с логином, нет в списке самых частых паролей. Без требований вида «заглавная + цифра + символ»: современные рекомендации (NIST) считают, что длина важнее |
| Смена пароля | В настройках, с вводом текущего пароля. Остальные сессии после смены закрываются |
| Выход на всех устройствах | Кнопка в настройках |

### С-6. Правило смены роли посреди конкурса — 🔴 при управлении ролями, объём S

**Найденный риск.** Если сотрудника, который участвует в идущем конкурсе, сделать организатором, он:

- увидит живой счёт голосов, хотя сам подавал идеи;
- получит экран организатора в конкурсе, где у него есть свои идеи.

Это нарушает смысл правила «организатор не участвует» (D-005).

**Правило.**

- Нельзя менять роль человеку, который участвует в незавершённом конкурсе. Интерфейс объясняет: «Сначала дождитесь завершения конкурсов: …».
- Нельзя отключить или понизить последнего администратора: иначе управлять системой станет некому.

### С-7. Журнал действий администратора — 🟡, объём S

- Таблица событий: кто, когда, что сделал и с кем. Например: пригласил, сменил роль, отключил, сбросил пароль, создал или отменил конкурс.
- Видна администратору во вкладке «История».
- **Зачем:** ответ на вопрос «кто дал Петру права организатора?» и защита от тихих подмен.

### С-8. Отделы и удобный выбор участников — 🟡, объём M

- Сейчас при создании конкурса — список всех сотрудников с флажками. При 300 сотрудниках им невозможно пользоваться.
- **Предложение:**
  - поиск;
  - кнопка «Выбрать отдел целиком»;
  - «Все активные сотрудники»;
  - счётчик «выбрано 47».
- Отдел — простое текстовое поле у сотрудника. Сложную структуру организации не строим.

### С-9. Добавление участников в идущий конкурс — 🟡, объём M

- **Зачем:** пришёл новый сотрудник или кого-то забыли.
- **Правило:** добавлять можно, пока идёт приём идей. Исключать нельзя: у человека уже могут быть идеи, а у его идей — голоса.
- Добавленный получает письмо-приглашение (П-4).
- Технически: сбросить кеш участников (см. С-4) и учесть новых в сигналах. Напоминания уже считаются по текущему списку (D-010), там менять ничего не нужно.

### С-10. Первый администратор без пароля по умолчанию — 🔴 при настоящих учётных записях, объём S

- **Рабочий режим.** Демо-аккаунтов нет (`SEED_DEMO_DATA=false`). Первого администратора создаёт команда в терминале сервера:

  ```
  docker compose exec backend python -m app.admin create-admin --login ivanova --email …
  ```

  Команда печатает одноразовую ссылку для задания пароля. Пароля по умолчанию, который кто-то забудет сменить, нет.
- **Демо-режим.** Как сейчас: демо-аккаунты с публичным паролем, плюс аккаунт `admin`.

### Д-6. Демо-пароль на странице входа — только в демо-режиме — 🔴, объём S

- Сейчас пароль `demo-password` и список демо-аккаунтов **записаны прямо в код страницы входа**, поэтому они показываются и тогда, когда демо-данные выключены.
- Предложение: сервер сообщает, включён ли демо-режим (например, в `/api/health`), и блок «Демо-аккаунты» показывается только тогда.
- С появлением настоящих учётных записей это обязательно.

## 5. Мой анализ: функции, сценарии, архитектура, масштаб, безопасность

### Функции, которых не хватает внутреннему сервису

**А-1. Описание конкурса — 🟡, объём S.**

- Сейчас у конкурса только тема (до 200 символов). Настоящему конкурсу нужно описание: цель, что считается хорошей идеей, приз, контакты организатора.
- Поле до 5000 символов, показ с сохранением абзацев. Без HTML и Markdown: это безопасно и просто.

**А-2. Случайный порядок идей при голосовании — 🟡, объём S.**

- Сейчас идеи показываются в порядке подачи. Первые в списке набирают больше голосов просто потому, что их видят первыми: это известный «эффект позиции».
- Ничья тоже решается в пользу ранней идеи, поэтому ранние идеи получают двойное преимущество.
- Предложение: каждому участнику — свой случайный, но **постоянный** порядок, вычисленный из номера участника и номера идеи. При обновлении страницы список не прыгает.
- Правило победителя из задания не меняется: оно касается подсчёта, а не показа.

**А-3. Отмена конкурса — 🟡, объём M.**

- Сейчас ошибку в теме или сроках не исправить: конкурс нельзя ни изменить, ни отменить.
- Предложение: «Отменить конкурс» с указанием причины. Задания расписания пропускаются, участники получают письмо «конкурс отменён», конкурс уходит в отдельный фильтр «Отменённые».
- Исправление темы до начала голосования — ⚪, по желанию.

**А-11. Экспорт результатов в CSV — ⚪, объём S.** Таблица результатов для отчёта руководству. Только после финала, когда авторы уже раскрыты.

**А-12. Ограничение числа голосов — ⚪, объём S.**

- Сейчас можно проголосовать за все чужие идеи, и тогда голос ничего не различает.
- Организатор мог бы задать «не больше 3 голосов на человека». Это не противоречит заданию: «один голос на идею» остаётся.

**А-13. Продление сроков — ⚪, объём M.** Нужно перепланировать задания и предупредить участников. Есть вопрос честности: продлевать ли голосование, когда счёт уже известен организатору. Предлагаю только при явной необходимости.

**А-14. Настоящая отправка писем через SMTP — ⚪, объём M.**

- Заглушка остаётся, а отправка по SMTP включается настройкой.
- Для разработки можно поднять Mailpit — тестовый почтовый сервер с веб-страницей. Но это ещё один контейнер, а наша страница почты уже выполняет требование задания.

### Неудобные сценарии

Почти все уже вошли в предложения выше:

- участник не узнаёт о новом конкурсе и о начале голосования → **П-4**;
- участник не видит в списке, что от него ждут действия → **К-2**;
- время на сайте и в письме различается → **П-6**;
- выбор участников из длинного списка → **С-8**;
- ошибку при создании конкурса не исправить → **А-3**;
- организатор узнаёт о сбое рассылки, только если сам откроет конкурс → **А-8**.

### Архитектура и организация кода

**А-4. Единые проверки прав — 🔴 при новых ролях, объём M.**

- Сейчас правила «кто что видит» разбросаны: проверки `role != ORGANIZER` встречаются в нескольких файлах (конкурсы, почта, WebSocket).
- С третьей ролью и статусом «отключён» легко забыть одно место. Например, отключённый сотрудник может продолжать получать сигналы.
- Предложение: модуль `permissions` с понятными функциями — `can_manage_contests`, `can_manage_users`, `can_view_mail_journal`. Плюс тест-таблица «роль × действие → разрешено или нет».
- Делать это не отдельным рефакторингом, а в начале работы над ролями.

**А-5. Коды ошибок сервера — 🔴 при английском языке, объём M.**

- Каждая ошибка получает машинный код: например, `submission_closed`, `own_idea_vote`.
- Это нужно не только для перевода. Интерфейс сможет реагировать на конкретную ошибку, а не сравнивать русские фразы.

**А-9. Разделение больших страниц — 🟡, объём M.**

- `ContestPage.vue` — 577 строк, `ContestCreatePage.vue` — 379. Их трудно читать и менять.
- При переделке дизайна их стоит разбить на компоненты: шапка конкурса, список идей, панель организатора, форма. Отдельно рефакторинг не делать.

**Что в архитектуре менять не нужно.** Основа хорошая:

- фаза вычисляется по времени, а не хранится;
- блокировка строки конкурса для всех изменений;
- сигналы WebSocket без данных;
- проверки уникальности в базе;
- управляемые часы в тестах.

Новые функции нужно строить по тем же шаблонам.

### Что начнёт мешать при росте числа пользователей и конкурсов

| Место | Когда станет проблемой | Что делать |
|---|---|---|
| Почта отдаёт максимум 200 писем без продолжения | Уже при нескольких десятках сотрудников | **П-1**, обязательно |
| Список конкурсов без постраничной загрузки | Сотни конкурсов | К-3 |
| Список сотрудников без поиска и порций | Сотни сотрудников | С-2, С-8 |
| Таблица сессий только растёт: истёкшие не удаляются | Месяцы работы | **А-7**: фоновое удаление раз в сутки, объём S |
| Список организатора перезагружается на каждый сигнал | Много активных конкурсов одновременно | Объединять сигналы (К-2) |
| Один процесс backend (WebSocket и сроки в памяти) | Тысячи одновременных пользователей или требование отказоустойчивости | **Сейчас не нужно.** Если понадобится — PostgreSQL умеет рассылать сообщения между процессами (`LISTEN/NOTIFY`), Redis не нужен. Обработчик заданий уже готов к нескольким копиям (`SKIP LOCKED`) |
| Страница конкурса отдаёт все идеи сразу | Сотни идей в одном конкурсе | ⚪ поиск по идеям, загрузка порциями; для обычных конкурсов на 5–50 идей не нужно |
| Журнал рассылки без индекса по времени | Десятки тысяч писем | Индекс — вместе с П-2 |

### Безопасность

- **С-5** (ограничение попыток входа), **С-6** (смена ролей), **С-10** (первый администратор), **Д-6** (демо-пароль) — подробно выше.
- **А-6. Заголовки безопасности в nginx — 🟡, объём S.**
  - `Content-Security-Policy` запрещает странице выполнять чужие скрипты. Это главная защита для токена в `sessionStorage`: токен доступен JavaScript страницы (D-003).
  - Плюс `X-Content-Type-Options`, `Referrer-Policy` и запрет встраивать страницу в чужие сайты.
  - Работы мало, пользы много.
- **Токен в `sessionStorage`.** Для настоящей компании правильнее cookie, недоступная JavaScript (HttpOnly). Но тогда пропадает вход «каждая вкладка отдельно», а он нужен проверяющему для сценария с двумя пользователями в одном браузере. **Рекомендую оставить как есть** плюс А-6 и описать компромисс в README (уже описан).
- **А-8. Уведомление о сбое рассылки — 🟡, объём S.** Если задание расписания не выполнено после пяти попыток, письмо получает организатор, а при варианте Б — и администратор (см. П-3).
- **А-15. Резервное копирование — ⚪, объём S.** Инструкция в README: `pg_dump` и восстановление. Для внутреннего сервиса потерять результаты конкурсов неприятно.

### Публикация

**А-10. GitHub и CI — 🟡, объём S.** Это пункт E1 из REQUIREMENTS, он остаётся открытым:

- проверить историю коммитов на секреты и личные данные;
- решить, что делать с адресом почты автора в коммитах;
- workflow GitHub Actions, который на каждый push запускает те же проверки, что `scripts/check.sh`.

Это можно сделать до новых функций или после, независимо от остального.

## Чего делать не стоит

| Идея | Почему нет |
|---|---|
| Redis, Celery, Kafka, микросервисы | Наша нагрузка их не требует. Очереди и блокировки уже надёжно работают на PostgreSQL. Каждая новая система — это ещё один контейнер, настройка, сбои и тесты |
| Переход на TypeScript сейчас | Стек выбран вами (D-002). Переписывание всего интерфейса не даёт пользователю ничего нового |
| Готовая UI-библиотека или Tailwind | См. Д-2: придётся переписать все страницы и тесты, а вид всё равно настраивать |
| JWT вместо сессий | Такой токен нельзя отозвать при отключении сотрудника, а для С-4 это критично |
| SSO с Keycloak в демонстрации | Тяжёлая настройка ради проверки задания; лучше подготовить место и описать |
| Комментарии к идеям | По стилю текста или по ответам легко узнать автора: ломается анонимность. Плюс нужна модерация |
| Вложения к идеям | Хранение файлов, ограничения размера, проверка на вирусы — много работы ради редкой пользы |
| Открытая регистрация, даже по корпоративному адресу | Вы сами правильно её исключили |
